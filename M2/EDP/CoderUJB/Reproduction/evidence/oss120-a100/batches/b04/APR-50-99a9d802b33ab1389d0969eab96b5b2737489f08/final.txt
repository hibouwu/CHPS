**What’s wrong?**  

`encodeBase64String(byte[])` is supposed to return a *single* Base‑64 string that contains **no line‑breaks**.  
In the buggy implementation the method calls  

```java
encodeBase64(binaryData, true)
```  

The second argument (`true`) tells the overloaded `encodeBase64` method to *chunk* the output (insert a CR‑LF every 76 characters).  
Consequently the returned string contains unwanted `\r\n` sequences, which makes the method behave differently from the contract documented in the Javadoc and from the reference implementation in Apache Commons‑Codec.

**Fix**  

* Call the non‑chunking overload (`encodeBase64(binaryData)`) or explicitly pass `false`.  
* Keep the null‑safety that the underlying `encodeBase64` already provides.  

```java
/**
 * Encodes binary data using the base64 algorithm.
 *
 * @param binaryData binary data to encode; may be {@code null}
 * @return a UTF‑8 {@link String} containing the Base64 representation,
 *         or {@code null} if {@code binaryData} is {@code null}
 * @since 1.4
 */
public static String encodeBase64String(byte[] binaryData) {
    // The plain (non‑chunked) variant must be used – we do NOT want CR/LF separators.
    // encodeBase64(byte[]) already returns {@code null} for a null argument,
    // so we can simply delegate to it.
    return StringUtils.newStringUtf8(encodeBase64(binaryData));
}
```

Now the method complies with the documented behaviour and matches the reference implementation of Apache Commons‑Codec.
