**Test case for `Compress‑COMPRESS‑264`**  
The test reproduces the problem described in the issue: a ZIP file that contains a **stored** (un‑compressed) entry `test.txt` whose contents are the ASCII string `"data\n"`.  
With Commons‑Compress 1.6 the entry is read correctly, while with 1.7 the first four bytes are returned as `0x00`.  
The test asserts that the data read from the first entry is exactly the expected byte sequence – any deviation (e.g. NUL bytes) will cause the test to fail.

            assertArrayEquals("The entry content is corrupted (e.g. NUL bytes)",

        }

### What the test does

| Step | Action | Expected outcome |
|------|--------|------------------|
| 1 | Wrap the raw byte array in a `ByteArrayInputStream` and feed it to `ZipArchiveInputStream`. | No exception – the stream is ready for reading. |
| 2 | Call `getNextZipEntry()` and check the returned `ZipArchiveEntry`. | The entry exists, its name is `test.txt`, and its method is `STORED`. |
| 3 | Read exactly `entry.getSize()` bytes from the stream. | The read loop finishes after the exact number of bytes (5). |
| 4 | Compare the read bytes with the expected UTF‑8 sequence `"data\n"`. | The arrays are equal. If Commons‑Compress 1.7 introduces NUL bytes, the assertion fails, reproducing the bug. |

Running this test against **Commons‑Compress 1.6** passes, while **1.7** (or any later version that still contains the defect) will fail, providing a regression‑safe verification for the issue.
