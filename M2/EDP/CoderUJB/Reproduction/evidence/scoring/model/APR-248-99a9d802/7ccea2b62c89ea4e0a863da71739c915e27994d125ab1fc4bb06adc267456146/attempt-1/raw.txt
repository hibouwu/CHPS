**Explanation**

`CSVPrinter.println()` is supposed to write the *record separator* (the line‑break that ends a CSV record).  
The original implementation simply does:

```java
final String recordSeparator = format.getRecordSeparator();
out.append(recordSeparator);
```

If the `CSVFormat` does **not** define a custom record separator, `format.getRecordSeparator()` returns `null`.  
Calling `Appendable.append(null)` throws a `NullPointerException`, which is the bug that surfaces when the printer is used with the default format.

The fix is to:

1. Detect a `null` record separator.  
2. When it is `null`, fall back to the default separator defined by the library (`CR` + `LF`).  
3. Keep the `newRecord` flag set to `true` after the separator is written (the original code already does this).

Below is the corrected method, together with a short Javadoc comment that clarifies the behaviour.

---

**Corrected `println` implementation**

```java
/**
 * Outputs the record separator.
 *
 * @throws IOException If an I/O error occurs.
 */
public void println() throws IOException {
    // The record separator may be user‑defined (e.g. "\n") or {@code null}
    // when the default (CR + LF) should be used.
    final String recordSeparator = format.getRecordSeparator();

    if (recordSeparator != null) {
        // Use the user‑provided separator.
        out.append(recordSeparator);
    } else {
        // No custom separator – fall back to the library default.
        out.append(CR);
        out.append(LF);
    }

    // After a record separator we are ready for a new record.
    newRecord = true;
}
```

**Why this works**

* `recordSeparator != null` → we safely append the supplied string.  
* `recordSeparator == null` → we explicitly append the two characters `CR` (`'\r'`) and `LF` (`'\n'`), which are the constants imported from `org.apache.commons.csv.Constants`.  
* No `NullPointerException` can be thrown because we never pass a `null` reference to `Appendable.append`.  
* The `newRecord` flag is correctly reset, preserving the original semantics.

With this change the `CSVPrinter` works correctly for both default and custom `CSVFormat` configurations.
