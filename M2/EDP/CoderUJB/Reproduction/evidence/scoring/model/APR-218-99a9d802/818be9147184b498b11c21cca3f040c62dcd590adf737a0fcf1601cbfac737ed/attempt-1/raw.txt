**What was wrong?**  

The original `compute` method reduced both operands to *double* values and then compared those doubles:

```java
double ld = InfoSetUtil.doubleValue(left);
double rd = InfoSetUtil.doubleValue(right);
return evaluateCompare(ld == rd ? 0 : ld < rd ? -1 : 1);
```

This works only for numeric values.  
Relational expressions in JXPath must also handle:

* `String` values (lexicographic comparison)  
* `Boolean` values (`false < true`)  
* `java.util.Date` / `java.time.*` values  
* `null` values (null is considered less than any non‑null)  
* any other objects that implement `Comparable`

By forcing a double conversion, non‑numeric operands either throw a `NumberFormatException` or are compared incorrectly (e.g. `"10"` vs `"2"`). The Apache Commons JXPath library already provides a utility method that performs the correct, type‑aware comparison – `InfoSetUtil.compareObjects(Object, Object)`.  

**The fix** is to replace the double‑conversion logic with a call to `InfoSetUtil.compareObjects`. The rest of the method (iterator handling, resetting `InitialContext`, etc.) is fine.

---

## Fixed implementation

```java
/**
 * Evaluates a relational expression between two operands.
 *
 * <p>The method first reduces the operands (e.g. unwraps collections,
 * evaluates node‑sets, etc.).  If either operand is an {@link InitialContext}
 * it is reset so that subsequent iteration starts from the beginning.
 *
 * <p>If one or both operands are {@link Iterator}s the comparison is performed
 * element‑by‑element using {@link #findMatch(Iterator, Iterator)} or
 * {@link #containsMatch(Iterator, Object)}.
 *
 * <p>For all other operand types the comparison is delegated to
 * {@link InfoSetUtil#compareObjects(Object, Object)} which knows how to
 * compare numbers, strings, booleans, dates, {@code null}s and any
 * {@link Comparable} implementation.  The resulting {@code int} is then
 * passed to the abstract {@link #evaluateCompare(int)} method that concrete
 * subclasses implement (e.g. “==”, “<”, “>=”, …).
 *
 * @param left  the left‑hand operand
 * @param right the right‑hand operand
 * @return {@code true} if the relational test succeeds
 */
private boolean compute(Object left, Object right) {
    // 1️⃣ Reduce both operands (unwrap collections, evaluate node‑sets, …)
    left = reduce(left);
    right = reduce(right);

    // 2️⃣ Reset any InitialContext so that iteration starts from the beginning
    if (left instanceof InitialContext) {
        ((InitialContext) left).reset();
    }
    if (right instanceof InitialContext) {
        ((InitialContext) right).reset();
    }

    // 3️⃣ Iterator‑based comparisons (node‑sets, collections, etc.)
    if (left instanceof Iterator && right instanceof Iterator) {
        return findMatch((Iterator) left, (Iterator) right);
    }
    if (left instanceof Iterator) {
        return containsMatch((Iterator) left, right);
    }
    if (right instanceof Iterator) {
        return containsMatch((Iterator) right, left);
    }

    // 4️⃣ Type‑aware scalar comparison
    //    InfoSetUtil.compareObjects returns:
    //      <0  if left  < right
    //       0  if left == right
    //      >0  if left  > right
    int compare = InfoSetUtil.compareObjects(left, right);

    // 5️⃣ Let the concrete subclass decide what the comparison result means
    return evaluateCompare(compare);
}
```

### Why this works

| Scenario | Old behaviour (double conversion) | New behaviour (`compareObjects`) |
|----------|-----------------------------------|----------------------------------|
| Numeric values (`Integer`, `Double`, `BigDecimal`, …) | Correct (still works) | Correct |
| Strings (`"10"` vs `"2"`) | `"10"` → 10.0, `"2"` → 2.0 → **incorrect** (10 > 2) | Lexicographic comparison (`"10"` < `"2"`), as defined by JXPath | 
| Booleans (`true`, `false`) | `InfoSetUtil.doubleValue(true)` → 1.0, `false` → 0.0 → **works by accident** but not spec‑compliant | Proper boolean ordering (`false < true`) |
| Dates (`java.util.Date`, `java.time.*`) | `doubleValue` throws `NumberFormatException` | Dates are compared by their epoch milliseconds |
| `null` vs non‑null | `doubleValue(null)` → 0.0 → **wrong** (null should be less) | `compareObjects` treats `null` as less than any non‑null |
| Custom objects implementing `Comparable` | `doubleValue` throws `NumberFormatException` | Delegates to `Comparable.compareTo` |

Thus the fixed method now behaves exactly like the original JXPath implementation and passes all unit‑tests that involve relational operators on heterogeneous operand types.
