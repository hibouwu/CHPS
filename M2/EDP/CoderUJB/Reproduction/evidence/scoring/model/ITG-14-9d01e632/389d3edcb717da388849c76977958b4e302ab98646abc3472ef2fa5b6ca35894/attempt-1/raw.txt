**JUnit 4 test that reproduces JacksonCore‑216 (ArrayIndexOutOfBoundsException 128) when the internal symbol table is forced to grow while repeatedly deserialising a JSON document that contains many distinct field names.**  

```java
package com.fasterxml.jackson.core.tests;

import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.Test;

import java.util.LinkedHashMap;
import java.util.Map;

import static org.junit.Assert.assertEquals;
import static org.junit.Assert.fail;

/**
 * Test for JacksonCore‑216 – “ArrayIndexOutOfBoundsException: 128 when repeatedly
 * serializing to a byte array”.  The problem occurs in {@code ByteQuadsCanonicalizer}
 * when the symbol table is expanded many times while parsing JSON that contains a
 * large number of distinct field names.
 *
 * The test creates a JSON document with a few thousand unique field names,
 * serialises it once to a byte array and then deserialises that byte array many
 * times.  If the bug is present an {@code ArrayIndexOutOfBoundsException}
 * (index 128) is thrown from {@code ByteQuadsCanonicalizer.addName}.  The test
 * asserts that no exception is thrown and that the data round‑trips correctly.
 */
public class JacksonCore216Test {

    @Test
    public void testSymbolTableExpansionBytes() throws Exception {
        // -----------------------------------------------------------------
        // 1) Build a map that contains a *large* number of distinct keys.
        // -----------------------------------------------------------------
        final int NUM_FIELDS = 2_000;               // enough to trigger expansion
        Map<String, Integer> original = new LinkedHashMap<>(NUM_FIELDS);
        for (int i = 0; i < NUM_FIELDS; ++i) {
            original.put("field_" + i, i);
        }

        // -----------------------------------------------------------------
        // 2) Serialise the map once – we keep the byte[] around so that the
        //    parser works on the same input for every iteration.
        // -----------------------------------------------------------------
        ObjectMapper mapper = new ObjectMapper();
        byte[] json = mapper.writeValueAsBytes(original);

        // -----------------------------------------------------------------
        // 3) Repeatedly deserialize the same byte array.  The parser will
        //    repeatedly add the field names to its symbol table; after enough
        //    iterations the table must grow without throwing the AIOOBE.
        // -----------------------------------------------------------------
        final int ITERATIONS = 5_000;   // large enough to expose the bug
        try {
            for (int i = 0; i < ITERATIONS; ++i) {
                // TypeReference is used so Jackson knows the generic type.
                Map<String, Integer> read = mapper.readValue(
                        json,
                        new TypeReference<Map<String, Integer>>() {}
                );

                // sanity‑check – the map must contain exactly the same data
                assertEquals("Iteration " + i + " produced wrong size", NUM_FIELDS, read.size());
            }
        } catch (ArrayIndexOutOfBoundsException e) {
            // If the bug is still present we fail the test with a clear message.
            fail("ArrayIndexOutOfBoundsException (index " + e.getMessage()
                    + ") was thrown while expanding the symbol table – JacksonCore‑216 reproduced.");
        }
    }
}
```

### Why this test works

* **Many distinct field names** – `ByteQuadsCanonicalizer` stores field names as
  “quads” (four‑byte chunks).  When the number of distinct names exceeds the
  initial bucket count the table must be resized.  The original bug caused the
  resize logic to write past the end of the internal array (index 128).

* **Repeated parsing of the same JSON** – each call to `ObjectMapper.readValue`
  re‑uses the same underlying `ByteQuadsCanonicalizer` instance (via the
  parser’s `SymbolTable`).  By looping thousands of times we force the table to
  grow many times, reproducing the overflow condition.

* **No exception expected** – the test will pass only if the parser can handle
  the growth correctly, i.e. the issue is fixed.  If the exception re‑appears the
  test fails with a helpful message.

You can drop this class into the Jackson core test suite (or any project that
depends on Jackson‑databind) and run it with your usual JUnit runner. If the
bug is still present you will see the `ArrayIndexOutOfBoundsException` as
described in the issue report.
