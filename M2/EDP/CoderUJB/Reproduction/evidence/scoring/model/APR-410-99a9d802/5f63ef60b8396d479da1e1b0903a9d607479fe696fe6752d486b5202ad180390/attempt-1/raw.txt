**Explanation of the problem**

`DateTimeFormatter.parseInto(..)` is supposed to modify the supplied
`ReadWritableInstant` **only when the parse succeeds**.  
The Javadoc of the method says:

> *If it fails, the return value is negative, but the instant may still be
> modified.*

In the original Joda‑Time implementation the instant is **not** updated
when the parser reports a failure – the caller can decide whether to keep
the partially‑filled instant or not.  
The buggy version always calls `bucket.computeMillis(..)` and writes the
result back to the instant, even when `parser.parseInto(..)` returns a
negative value (parse failure). This can leave the instant in an
inconsistent state (e.g. a partially‑parsed date that does not correspond
to the original instant).

**Fix**

1. Store the result of `parser.parseInto(..)` in `newPos`.  
2. Apply the changes to the instant **only if** `newPos >= 0`.  
   When the parse fails we simply return the negative position and leave
   the instant untouched.  
3. The rest of the method (chronology/zone handling) is also guarded by
   the same condition, because those changes are only meaningful when a
   successful parse has produced a new millisecond value.

**Corrected code**
