## 先问瓶颈在哪里，再问能否不用锁（第 1–3 页）

若单线程时间为 T，其中比例 p 可以完全并行，理想 n 线程时间为

$$
T_n=T\left((1-p)+\frac pn\right),\qquad
S_n=\frac{1}{(1-p)+p/n}.
$$

当 n 增大，串行部分留下的加速上限为 $1/(1-p)$。p=0.75 时上限只有 4；p=0.95 时上限为 20。按式代入，32 核时分别约 3.66 和 12.55，后一情形在 128 核时约 17.41。课件的 3.7、17.42 是近似数。这里 p 是基准执行时间中的比例，不应简单数源代码行数；模型也未计入并行新增的通信和同步开销。

锁可能让一个暂停的持有者阻挡所有等待者。非阻塞算法尝试提供不同的进展保证：

| 保证 | 关心谁能完成 | 不能据此推出什么 |
|---|---|---|
| wait-free | 每个继续执行的操作都能在有界的自身步骤内完成 | 不能给出包含系统抢占的固定墙钟时间 |
| lock-free | 系统持续执行时，总有操作持续完成 | 不能保证某个指定线程不饿死 |
| obstruction-free | 某个操作从当前状态独自执行足够久时能完成 | 多线程一直冲突时不一定有人完成 |

强弱关系为 wait-free ⇒ lock-free ⇒ obstruction-free。假设一个线程停在持锁状态，另一个线程即使独自运行也拿不到锁，这说明普通阻塞锁为什么不满足最弱一项。反过来，“源代码里没有 mutex”不构成 lock-free 的证明。

## 栈：把头指针当作一次操作的提交点（第 4–11 页）

栈遵守后进先出。每个节点有元素和 `next`；共享 `head` 指向栈顶。带锁版本先完成节点链接，再更新头，整个过程位于临界区。非阻塞版保留同样的状态变化，但用 CAS 检查“我用来计算新状态的旧头还有效吗”。

以压入 D 为例：读到旧头 C，构造 `D.next=C`，尝试把头从 C 改成 D。如果期间别的线程已经把头改成 X，CAS 失败，必须重新读取头并重新准备链接。不能在失败后继续使用旧的 `D.next=C`，否则可能把 X 丢掉。

弹出时读旧头 n，若为空则返回空或报错；否则尝试把头从 n 改成 `n.next`。成功 CAS 是非空弹出的**线性化点**：可以把并发操作看成在这个瞬间按某个顺序发生。

```text
教学伪代码：CAS 返回旧值；暂不考虑节点回收
push(e):
    n = new Node(e)
    repeat:
        old = atomic_read(head)
        n.next = old
    until CAS(&head, old, n) == old

pop():
    repeat:
        old = atomic_read(head)
        if old == null: return EMPTY
        next = old.next
    until CAS(&head, old, next) == old
    return old.element
```

**与原文的区别：** 第 9–11 页在每次重试时都 `new Node`，教学版将分配移到循环外，失败后重设链接。课件局部变量跨出 `do` 的作用域、混用类与 C 地址符号等，也表明它不是可直接编译的语言程序。第 10 页尚未检查空栈，第 11 页才补上，应以完整阶段理解。

![栈的 CAS 与进展说明](Images/03-non-blocking/pdf_p011.png)

若自己的强 CAS 因头变化而失败，说明别的更新已经取得进展。这个论证依赖 CAS 及内存管理等底层步骤满足相应假设。它不保证自己最终成功：别人可能总在自己之前改变头。因此该结构的更新核心是 lock-free，而不是 wait-free。

## 队列为什么比栈多一个困难（第 12–19 页）

队列先进先出，入队改尾部，出队改头部。带锁版本可以把“原来为空时同时改 head 和 tail”包在临界区内，但单字 CAS 不能一次修改两个独立指针。

课件保留一个哨兵节点（fake/dummy），使 `head` 始终指向当前哨兵，`head.next` 才是第一个有效元素。`tail` 只是帮助定位末端的指针，允许滞后。三个关键不变量是：head 的后继是第一个有效元素；从 head 和 tail 出发的链至少相交；最终沿 `next` 到达的是已入队链的末端。

![允许尾指针滞后](Images/03-non-blocking/pdf_p018.png)

**图解：** 第 18 页甚至允许 tail 落后于当前 head。别把这份教学算法的 tail 不变量替换成“tail 永远是最后一个节点”。这也意味着旧节点仍可能用于向后追赶，不能在出队后随意释放。

## 单个入队如何完成（第 20–23 页）

初始时 head 和 tail 都指向同一个哨兵。构造元素 A 的新节点，其 `next` 为空。入队者从 tail 出发，若发现 `next` 非空，就帮助 tail 向后追赶；找到末端后，CAS 把该末端的 `next` 从空变成新节点。

**把空的 `next` 改成 A 的那次成功 CAS，才是入队的线性化点。** 后面尝试将 tail 移到 A 只是维护辅助指针。即使这个 tail CAS 失败，也不需要撤销已经成功的入队，因为其他人可能已经帮忙移动了它。

## 两个入队者如何互相帮助（第 24–36 页）

动画让 B 和 C 同时准备接到 A 后面。它们都可能观察到 `A.next==NULL`，但只有一个能成功把它改成自己的节点。假设 B 先接入，却在更新 tail 前暂停：

| 步骤 | 已连成的链 | tail 的可能位置 | C 该做什么 |
|---|---|---|---|
| B 尚未链接 | fake → A | A | 尝试空 next |
| B 链接成功 | fake → A → B | 仍为 A | 发现 A.next 非空 |
| C 帮助追赶 | fake → A → B | 推进到 B | 沿新末端继续 |
| C 链接成功 | fake → A → B → C | B 或 C | 尝试推进 tail 后返回 |

![C 帮助 B 推进尾指针](Images/03-non-blocking/pdf_p031.png)

**图解：** 图上的法语旁注指 C 替 B 完成 tail 的推进。这是帮助机制：操作不要求最先发起修改的线程亲自完成所有后续维护。紫色链表示已经连接的节点，单独浮着的新节点尚未入队。

## 出队为什么移动的是哨兵（第 37–40 页）

读取旧 head 为 res，若 `res.next` 为空，队列在该观察点为空；否则尝试把 head 从 res 改成 `res.next`。成功后返回后者的元素。该节点成为新的哨兵，旧哨兵退出有效队列路径。

![A 成为新哨兵](Images/03-non-blocking/pdf_p039.png)

**图解：** 返回 A 的值，不等于把 A 的节点立即删掉。新的 head 正指向 A，下一次出队从 A 的后继取值。第 37–39 页使用 `value`，前面的结构定义写 `element`，这是原课件字段命名不一致，教程统一称元素值。

进展论证要分别看两类 CAS：连接新节点或推进 head 直接完成一个操作；推进 tail 是帮助，可能只是中间进展。不能把“任何 CAS 失败”一概解释为“别人已经返回一个完整操作”。需要结合有限链追赶和成功更新分析，才能得出总体 lock-free 结论。

## 有序链表：删除为什么要分两步（第 41–48 页）

考虑 `A → B → C`。线程甲想删除 B，计划把 A 的后继改成 C；线程乙想在 B 后插入 X。如果甲先读了旧后继 C，而乙已经把 X 接到 B 后面，甲随后直接绕过 B，就可能一起丢掉 X。

课件采用 Harris 式思路：先把 B **逻辑删除**，再由任意遍历者将 B **物理摘链**。节点有白/灰两种状态，灰色表示逻辑上已删除。

标记必须与 B 的 `next` 放在同一个可 CAS 的值中。否则插入者只检查 next 是否没变，无法知道 B 已经被删除。课件用指针最低位作标志：

```text
pointer(v) = v 去掉最低位
mark(v)    = v 的最低位
```

第 48 页的 `ptr & -2` 表达清除最低位的意图。在具体 C 实现中须确认对齐保证、`uintptr_t` 与掩码类型、指针表示及原子访问方式；图中的位操作不自动在所有平台上成立。标的是**当前节点自己的 next 域**，不是随意给前驱链上的箭头加颜色。

## 遍历与帮助摘链（第 49–59 页）

`pred` 不只是前驱节点，它是“指向当前节点的那个链接字段的地址”。所以开头可等于根指针的地址，往后则变成 `&cur->next`。这个间接层让删除头节点与删除中间节点使用同一种操作。

遍历到灰色节点 cur 时，CAS 尝试把 `*pred` 从 cur 改成 cur 的真实后继。成功后继续检查同一个 pred 所指的新节点；失败则重新寻找，原因可能是前驱已被标记，或者中间已经插入新节点。这里 `continue` 不应误读为跳过一个后继，否则会漏查。

## 删除 17：操作成功与摘链成功不是一回事（第 60–67 页）

在 `12 → 17 → 22` 中寻找 17，先读取 17 的 next，再 CAS 把该值改成“同一指针加删除位”。这次成功标记可以作为逻辑删除的线性化点。随后尽力把前驱链接改为 22。

![先标记，再帮助摘链](Images/03-non-blocking/pdf_p060.png)

如果另一个线程恰好在 12 与 17 之间插入 14，原来的摘链 CAS 会失败。课件第 65–67 页说明：即使 17 仍物理地在链上，逻辑删除已经完成，未来遍历者可以帮忙清除。不能因为没有立即摘掉节点，就报告删除从未发生。

第 68–69 页补全“没找到”的处理：到达空指针，或当前值已经大于目标值，可以停止。例如找 13，走到 17 即可判断不存在。这个结论依赖链表有序。

**原文边界：** 课件逐步代码包含未显示初始化的 `found`、未声明临时量，以及 `void` 函数中 `return 0` 等语言层不一致。它说明遍历与重试机制，并未定义完整集合 API，重复删除时的布尔返回值也需要额外设计。

## 插入 14：验证连接点仍有效（第 70–75 页）

寻找第一个大于 14 的节点，构造 `14.next=17`，然后 CAS 将前驱链接从 17 改成 14。成功 CAS 是插入的线性化点。如果前驱 12 被标记删除，它自己的 next 域会带标志，不再匹配未标记的期望值；如果别人已插入节点，也会不匹配。两者都应触发重找位置。

![插入 CAS 可能失败的两种原因](Images/03-non-blocking/pdf_p073.png)

**图解：** 插入所修改的是 pred 指向的链接，不是 cur 自己的 next。原图把“12 变灰”和“12、17 之间已有新节点”作为两个失败原因。课件没有拒绝相等键，因此它不能未经修改就被当作“不含重复值的集合”。

## 从教学图走到真实程序，还差内存回收（第 76 页及补充）

本讲最后强调进展等级、数据结构不变量和线性化点。学习时应能为每个成功操作指出提交效果发生在哪里，也能说明失败重试是否代表其他线程取得进展。

**补充，非原课件完整展开内容：** 逻辑删除、物理摘链、释放内存是三件事。一个节点已经不在链上，另一个线程仍可能持有旧指针。立即 `free` 会造成释放后使用；地址被回收再复用，还可能使 CAS 看到同一地址值而误以为状态没变，这就是常见的 ABA 风险。仅给指针加版本号，并不能单独解决旧指针解引用的安全性。

因此本讲的论证先假设节点在使用期间有效，并且不会发生破坏假设的地址复用。真实系统需要垃圾回收、hazard pointers、epoch 等适当机制，并检查内存分配及回收是否改变整体进展保证。这里点明缺口，不假装已经实现完整回收算法。[Michael 的 hazard pointers 论文](https://research.ibm.com/publications/hazard-pointers-safe-memory-reclamation-for-lock-free-objects)

对应实验：[非阻塞算法](../Labs/tp-non-blocking/tp-non-blocking.html)。开始写代码前，先画出读指针、验证指针、使用节点与释放节点的关系。

## 自检与判断要点

1. **某个线程不断 CAS 失败，是否反驳 lock-free？** 不一定；系统可能一直有其他操作完成，但它不是 wait-free。
2. **压栈失败后为什么要重设 next？** 旧的头可能已经变化，重用旧 next 会丢失别人的更新。
3. **入队真正完成在更新 next 还是 tail？** 在末端空 next 被成功改成新节点时；tail 更新是维护动作。
4. **出队后原第一个有效节点为什么还在？** 它成为新哨兵，返回其值与删除该节点内存是不同的事。
5. **删除位为什么和 next 一起 CAS？** 插入必须同时验证后继和当前节点是否已删除，分开验证存在竞态窗口。
6. **标记成功、摘链失败，删除是否一定失败？** 否，逻辑删除已发生，其他线程可以帮助物理摘链。
7. **能找到线性化点是否就等于完成正确性证明？** 不等于；还要证明不变量、返回值、所有分支以及对象生命周期，并单独分析进展保证。
