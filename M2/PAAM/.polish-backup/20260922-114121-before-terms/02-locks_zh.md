## “看一眼空闲，再写成忙碌”为什么不够（第 1–4 页）

上一讲把互斥交给了 pthread mutex。这一讲从它内部需要完成的动作出发：检查锁是否空闲，然后取得它。

设线程甲刚读到空闲便被暂停，线程乙也读到空闲，并将锁设为忙碌、进入临界区。甲恢复以后若照旧设置状态，也会进入。同一个空闲状态被两人接受，问题就发生在检查与设置之间。即使单次读写各自原子，组合起来仍需要额外保证。

原子操作使这类动作对其他线程表现为一个不可分割的效果。课件用“看起来在一个瞬间完成”描述它，关心的是观察结果；实现仍然需要时间。为了实现 mutex，我们要找到足以完成这种不可分割更新的底层机制，不能再假设已经有一把 mutex 可以保护它。

**原课件勘误，第 2 页：** 图中确实写了 `while (mutex->state == FREE) { }`。若含义是等待锁空闲，判断应当针对 `BUSY`。但仅改条件仍不能构成正确的锁，因为检查和设置之间仍有竞争窗口。同页 `#define ... = { FREE };` 也不是应当照抄的初始化宏写法。这些都是 PDF 原文问题，不是 OCR 把字符识别错了。

## 必须先说清机器允许什么（第 5–8 页）

讨论算法前，先固定用于推理的机器模型。课件暂时假设机器字的读写不可撕裂，指令也按指定顺序被观察。第一个条件表示：变量从 `0` 写成 `0x101` 时，读取者得到完整旧值或完整新值，不会得到由两者拼出的部分结果。

第二个例子先写 `x=0x101`，后写 `y=0x202`；另一个线程先读 `y` 再读 `x`。在所设模型中，如果读到新 `y`，接着就应读到新 `x`。第 6、8 页用覆盖式警告说明这些假设不能不加条件地推广到所有硬件。

**读图说明：** 第 8 页底层被覆盖的文字与第 7 页关系式不一致；教程采用第 7 页清晰的条件关系 `t2 == 0x202 ⇒ t1 == 0x101`。不能把第 8 页被遮挡文字重新拼成另一个结论。

## Bakery：怎样不用原子加一也能排队（第 9–13 页）

Bakery 算法用排队取号决定谁先进入临界区。每个线程扫描现有号码，取最大值加一，再与竞争者比较。由于扫描和取号并非一个整体，两个线程可能同时选中相同号码，所以还需要线程编号来区分先后。

比较规则是按 **(号码，线程编号)** 排序：先比较号码，号码相同再比较编号，较小者优先。号码 0 单独表示该线程没有参与竞争。

`num[i]` 是线程 i 的号码；`entering[i]` 表示它还在取号过程中。一个线程的典型步骤是：

1. 把自己的 `entering` 设为真；扫描号码，写入自己的号；再把 `entering` 设为假。
2. 对每个竞争者，等它完成取号；若它持有优先于自己的非零号码，就等待。
3. 所有更优先的竞争者退出后进入临界区；离开时把自己的号码改成 0。

`entering` 解决取号尚未完成的窗口。设线程 2 已计算出最大值加一，却还没写回；线程 3 此时仍看到旧数组，也取得同一个号并进入临界区。线程 2 恢复后写入号码，又会因为自己的编号更小而认为应当先走。

因此，比较号码之前必须先等对方完成取号。线程 3 若看到 `entering[2]` 为真，就知道还不能依据当前号码作决定。

![Bakery 原课件代码](Images/02-locks/pdf_p011.png)

**原课件勘误：** 第 11 页 `if (entering[i]) { }` 是空条件语句，不会等待，和旁边注释及第 12 页的论证不符。教学解释应为“持续等到 `entering[i]` 变假”，例如 `while (entering[i]) { }`；原文保留该差异。第 13 页解释中写“maximum number”也不能理解为最大号先进入，算法比较的是较小的非零二元组优先。

先只看已经完成取号的竞争者，二元组给出了唯一的先后顺序。若两个线程都能越过对方进入，就需要各自的二元组都小于对方，这与严格全序矛盾。完整证明还要覆盖取号与扫描相互交错的过程；前面的 `entering` 正是在处理这部分。

这个推理使用的是课件设定的抽象机器。写成 C 时，相关状态需要合适的原子对象与内存顺序，不能让普通 `int` 数组发生跨线程竞争读写。[Lamport 原始论文](https://lamport.azurewebsites.net/pubs/bakery.pdf)

取号和比较都要扫描竞争者的状态，因此单轮访问量随线程数 N 增长，数量级为 O(N)。一旦需要等待，扫描还可能重复。原课件的“至少四次”是在说明特定步骤的访问数量，并没有给出包含全部等待过程的固定成本。

## 缓存一致性为什么影响锁的速度（第 14–20 页）

Bakery 已经给出了一种互斥办法，接下来要理解它为什么可能慢。读写共享状态会触及 CPU 缓存，而缓存通常以整行为单位维护数据，课件以常见的 64 字节行为例。

同一行可以在多个核中保留共享副本。一个核需要写入时，要先取得对应写权限，使其他不再有效的副本失效。课件用多个读者或一个写者来概括这种协调；这是缓存一致性的简化模型，硬件并未逐行调用软件读写锁。

![两个核写同一缓存行](Images/02-locks/pdf_p017.png)

**图解：** 两个线程分别写 `tab[0]` 和 `tab[1]`，逻辑上没有写同一元素，却可能在同一缓存行上竞争。图中各自持有旧副本、各改一部分的画法用于解释为什么必须有一致性协议，不是说正常硬件任意丢写。

第 18 页的读缺失、写缺失和共享行转写，可以从同一个角度理解：这个核是否已经拥有所需的数据和权限，还是要与别的核通信。多个核反复写同一锁字时，所属缓存行便可能在它们之间来回转移。临界区很短，也可能因为频繁交接而无法继续提高吞吐量。

## 原子性与顺序是两件事（第 21–29 页）

缓存协议之后，还要分清原子性与内存顺序。对 `_Atomic` 对象使用 `atomic_load`、`atomic_store`，首先是为了保证对象访问的原子性。一次读取没有被撕裂，并不足以说明它与其他变量的更新有什么先后关系。

例如接收者看到了有消息标志，还需要知道发送者先前写入的消息内容是否已经可见。内存顺序就是用来建立这类推断的。

课件第 23 页列举读读、写写、写后读、读后写等顺序关系；第 24–26 页比较 TSO、较弱模型和屏障。这里的机器举例及 Java 说法均为教学概括，不能直接用来证明一段有 C 数据竞争的程序正确。具体指令、内存类型及对齐限制应以处理器手册为准。[Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)

以“先写消息，再设置有消息标志”为例，即使目标硬件保存相关顺序，编译器和语言层也仍需正确的同步关系。第 24 页标为“Correct code”的普通 C 风格片段不能作为可移植的 C 并发实现；第 25 页“Java 中段错误”也只是提示发布错误风险，不能按 C 的故障形式解释 Java 语言行为。

`relaxed` 保留原子对象自身的原子性与修改顺序，但单靠它不能发布其他对象。设两个原子变量初值为 0：线程 1 先写 `x` 再写 `y`，线程 2 先读 `y` 再读 `x`。如果只用 relaxed，读到新 `y`、旧 `x` 仍是允许的，因为这里没有建立从一个对象的观察到另一个对象的同步关系。

第 29 页的警告标注曾被 OCR 混进代码，应单独阅读。还要注意，普通非原子对象上的 C 数据竞争会导致未定义行为，不能将其后果仅概括成可能读到拼接值。

课件列出的各个 `memory_order` 并非可以随意用于每一种操作。例如普通 atomic load 不能指定 release，普通 atomic store 不能指定 acquire；acq_rel 用于适合的读改写等操作。更弱顺序需要证明，不能只凭一次测试没出错就采用。

## Release–acquire：用一个原子对象发布一组数据（第 30 页）

现在为消息发布补上同步关系。发送者先完成 `z=1`、`y=17`，再对原子 `x` 做 release 写入 42；接收者用 acquire 读取 `x`。只有这次读取确实取得相应发布的值，才能通过这条同步关系使用发布前写好的 `y`、`z`。这里还假设没有其他冲突写入。

```c
/* 教学片段：x 是原子变量；y、z 仅由发布者在发布前写入。 */
/* 线程 1 */
z = 1;
y = 17;
atomic_store_explicit(&x, 42, memory_order_release);

/* 线程 2 */
if (atomic_load_explicit(&x, memory_order_acquire) == 42) {
    /* 此处再读取 y 和 z */
}
```

数据初始化 → release 发布 → 读到该发布的 acquire → 使用数据，这几步组成了读者所依赖的顺序。**关键是 acquire 确实读到了相应发布，而不仅是两边都写了内存顺序参数。** 上面的条件分支将使用数据放在确认发布之后，便于看清这一前提。

**原课件勘误：** PDF 第 30 页两个 atomic 接口的 `x` 前均缺少 `&`，且无条件读取普通 `y`、`z`。若 acquire 没有读到发布值，这些读取就没有获得所需同步。上面增加了条件，是明确标注的教学修正版，不是声称原图已经这样写了。

## Consume 与顺序一致性：两处需要认真勘误的例子（第 31–33 页）

consume 的原始设计关注沿读取结果延续的数据依赖，例如取得已发布的指针，再通过该指针访问对象。**第 31 页不能用于证明它给出的结论：** 原图把 `z` 声明为普通 `int` 却用于原子接口，而且读线程后面的 `r3=x` 并不依赖于刚刚读到的 `r1`。写线程中 `x` 到 `z` 的关系不能替代读取端的依赖链。这里保留概念说明，不把该片段改名后作为正确样例。[WG14 内存顺序说明](https://open-std.org/jtc1/sc22/wg14/www/docs/n1525.htm)

顺序一致性要求相关原子操作可以放进一个兼容线程内顺序的共同顺序。它并不要求多个线程每次看到同样的“快照”。

**第 32 页反例：** 原图两个读线程都是先读 `x` 再读 `y`，却说线程 3 得到 `(1,0)` 后，线程 4 不可能得到 `(0,1)`。实际上以下全序完全满足顺序一致性：

```text
线程4读 x→0
线程1写 x=1
线程3读 x→1
线程3读 y→0
线程2写 y=1
线程4读 y→1
```

逐行检查这个交错，两位读者都保持了先读 x 再读 y 的顺序，所有操作也能放在同一个全序中，所以它足以反驳原页的不可能结论。问题来自原例子的逻辑，OCR 并未造成这一点。

通常用来展示相反写序观察的例子，会让两个读线程按相反的变量顺序读取，并相应设置结果条件。那是另一个例子，不能直接用它替换原页后声称原图正确。

**后续课件默认使用顺序一致的原子读写。** 第 33 页说明，为了简化表达，很多显式原子调用会从伪代码中省略。阅读下面的锁和下一讲的数据结构时，要一直保留这个约定；写实验的 C 实现时，再把原子类型与接口明确写出。

## 原子读改写与自旋锁（第 34–40 页）

`atomic_exchange` 原子地换入新值并返回旧值。假设 FREE=0、BUSY=1，多线程同时交换 BUSY 时，只有真正从 FREE 改成 BUSY 的那个调用能得到旧值 FREE，因而只有它获锁。

```c
/* 课件算法片段，按默认 seq_cst 解释。 */
while (atomic_exchange(lock, BUSY) != FREE) { }
/* critical section */
atomic_store(lock, FREE);
```

拿不到锁的线程会继续执行 exchange。即使锁已经是 BUSY，这仍然是一次读改写，会争夺同一缓存行的写权限。低争用时，获取路径很短；高争用时，大量失败尝试却可能把时间耗在缓存通信上。

第 38 页用写失效和排序开销解释这一现象，但“原子性本身没有任何性能成本”的说法过于绝对。真实硬件还需考虑指令延迟、吞吐和实现资源，不能从这页推出普遍的零成本结论。

对于恰当实现的这一简单锁，成功获取使用 acquire、释放使用 release 可以提供临界区之间的可见性。这个结论不能自动推广为“所有算法都可以统一把 seq_cst 换成 acquire/release”。

## Ticket lock：写一次取号，随后只读等待（第 41–46 页）

Ticket lock 让每个线程先取得自己的序号，再等待轮到自己。它用到 `atomic_fetch_add`：将共享变量加上增量，同时返回加之前的值。这样，竞争者能获得不同的号。

锁里分别保存 `ticket` 和 `screen`：前者发号，后者表示当前可以进入的号码。

线程原子地取号，然后等待屏幕显示自己的号；离开时使屏幕进入下一号。课件用 `< my` 检查等待，在号码单调且不回绕的教学假设下可读懂。工程实现常用无符号计数和相等性比较，并明确回绕及同时在队列中的线程数限制，不能忽视有限整数范围。

与 exchange 自旋不同，等待时读取 `screen` 可以利用本地共享副本。但所有等待者仍在同一位置上等待，每次屏幕更新都可能引起多个核重新读取。若 `ticket` 与 `screen` 放在同一行，取号操作也可能干扰等待者，这是布局时需要额外分析的因素。

课件提到 Linux 内核使用 ticket lock，属于历史背景，不代表所有现行内核与架构仍采用同一实现。

## MCS：让每个线程等自己的标志（第 47–52 页）

先理解 CAS：给定地址、期望值和新值，只有当前值匹配期望时才写入。C 的 `atomic_compare_exchange_strong` 返回真假；失败时还会把观察到的当前值写回 `expected`。第 48 页函数体中误拼为 `..._string`，标题中的 `..._strong` 才是实际名称。

Ticket lock 的等待者虽然主要在读，仍然盯着同一个 screen。MCS 把等待位置分散到每个线程自己的节点中，节点包含 `next` 和 `isFree`。课件使用 `_Thread_local`，让每个线程各有一份节点；全局 `lock` 则记录队尾，用来把新到的线程接进队列。

获取过程：初始化节点，将队尾原子交换成自己。如果原队尾为空，可以直接获得锁；否则把自己接到前驱的 `next`，然后反复读取自己的 `isFree`。释放者只需向直接后继写一次许可，而不必让所有等待者争抢同一个锁字。

![MCS 获取](Images/02-locks/pdf_p051.png)

图中入队包含两步：新等待者先通过交换取得队尾位置，再把前驱的 `next` 连到自己。线程可能在两步之间被暂停。这时，前驱看见的后继链接还是空的，但全局队尾已经指向后来者。

释放锁时必须区分这种情况与队列确实没有后来者的情况，具体步骤如下：

1. 若 `my.next` 为空，尝试 CAS 把队尾从自己改为空。成功说明没有后来者取得队尾，可以结束。
2. 若 CAS 失败，后来者已改队尾，但可能还没把链接写入自己的 `next`，因此等待该链接出现。
3. 得到后继后，设置后继的许可标志，完成交接。

![MCS 释放中的窗口](Images/02-locks/pdf_p052.png)

**校对说明：** 原图旁注说“head of the queue”，但这次 CAS 实际比较的是全局队尾。教程按代码的作用解释。简化版每线程只有一个节点，不能直接用它同时嵌套获取多个 MCS 锁；节点的存活期也必须覆盖排队与交接。

MCS 按队列顺序交接锁，因此其公平性体现为先后次序。如果下一位等待者被调度器暂停，排在后面的人仍可能一起等待，形成 convoy（队列拖延）；FIFO 并没有给出固定的等待时长。

把自旋分散到各自节点能减轻共享写热点，但入队和交接依然需要通信。节点布局也影响效果：多个节点挤在同一缓存行时，仍可能出现伪共享。

## 将三种锁放在一起（第 53 页）

| 锁 | 获取依据 | 等待位置 | 主要限制 |
|---|---|---|---|
| exchange 自旋 | 一次原子交换拿到 FREE | 同一锁字，反复读改写 | 高争用写热点；不保证公平 |
| ticket | 原子取号，等待轮到自己 | 所有人读同一个屏幕 | 广播式失效；队首暂停影响后续 |
| MCS | 原子入队，前驱交接 | 每个线程自己的标志 | 节点管理、交接窗口、convoy |

对应实验：锁算法（[中文版](../Labs/tp-locks/tp-locks_zh.html) · [英文原版](../Labs/tp-locks/tp-locks.html)）。课件以自旋锁为主，实验还涉及 futex；理解自旋与阻塞的取舍后再进入实验中的睡眠/唤醒路径。

## 自检与判断要点

1. **原子 load 加原子 store 是否等于 exchange？** 否，两次操作之间能插入别的线程动作。
2. **Bakery 为什么比较二元组？** 取号不是一个全局原子加一，可能同号；线程编号提供确定的破同号规则。
3. **relaxed 是否允许读到半个原子整数？** 不允许；缺少跨对象发布关系不等于缺少原子性。
4. **读取到 release 发布值有什么用？** 对应的 acquire 可使发布前的初始化先于读线程后续使用；仍须排除其他不受保护的冲突访问。
5. **第 32 页的反例为什么有效？** 两个读线程可以跨不同时间区间读取；它们的结果仍能嵌入一个合法全序。
6. **MCS 为什么不能看见 `next==NULL` 就直接返回？** 后继可能已交换队尾，却尚未连接前驱。
7. **MCS 每个线程等自己的变量，是否就完全没有通信？** 否，入队、链接与交接仍通信，只是避免所有等待者持续写同一位置。
