## 先问瓶颈在哪里，再问能否不用锁（第 1–3 页）

增加线程以前，先看程序有多少工作仍须串行完成。将单线程总时间记为 T，可完全并行的比例记为 p：串行部分不会随线程数减少，理想的并行部分则由 n 个线程均分，于是得到

$$
T_n=T\left((1-p)+\frac pn\right),\qquad
S_n=\frac{1}{(1-p)+p/n}.
$$

当 n 增大，串行部分留下的加速上限为 $1/(1-p)$。p=0.75 时上限只有 4；p=0.95 时上限为 20。按式代入，32 核时分别约 3.66 和 12.55，后一情形在 128 核时约 17.41。课件的 3.7、17.42 是近似数。这里 p 是基准执行时间中的比例，不应简单数源代码行数；模型也未计入并行新增的通信和同步开销。

缩短串行部分是性能动机，减少对某个线程的依赖则是另一个问题。假如持锁线程被暂停，等待者即使一直获得 CPU，也可能全部停在获取锁的地方。非阻塞算法讨论的进展保证，就是要说明在不同干扰条件下，哪些操作仍能完成。

| 保证 | 关心谁能完成 | 不能据此推出什么 |
|---|---|---|
| wait-free | 每个继续执行的操作都能在有界的自身步骤内完成 | 不能给出包含系统抢占的固定墙钟时间 |
| lock-free | 系统持续执行时，总有操作持续完成 | 不能保证某个指定线程不饿死 |
| obstruction-free | 某个操作从当前状态独自执行足够久时能完成 | 多线程一直冲突时不一定有人完成 |

这三个保证依次减弱：wait-free ⇒ lock-free ⇒ obstruction-free。判断它们时，可以先问指定线程能否完成，再问系统中是否总有人完成，最后问一个线程不再受干扰时能否完成。

普通阻塞锁连最后一项也可能做不到：某线程拿锁后停住，另一个线程即使独自执行，也无法替它释放锁。另一方面，删除 mutex 调用本身并不能证明进展，仍要分析重试循环会因什么结束。

## 栈：把头指针当作一次操作的提交点（第 4–11 页）

从结构最简单的栈开始。共享 `head` 指向栈顶，每个节点保存元素和 `next`，沿 next 可以找到更早压入的节点。

带锁版本先构造新链接，再更新 head，并把整个过程包在临界区内。非阻塞版本仍做这些事，只是在更新 head 时增加一次 CAS 验证：准备新链接期间，别人是否已经改过头指针。

假设当前栈顶是 C，我们准备压入 D。先令 `D.next=C`，再尝试把头从 C 改为 D。如果另一个线程抢先把 X 放到了栈顶，这次 CAS 就会失败。

下一轮需要重新读取头，并让 D 连向新的栈顶。若仍沿用旧的 `D.next=C`，即使后来成功发布 D，也可能把 X 从链中丢掉。**重试必须重新准备依赖共享状态的那部分结果。**

弹出的过程反过来：读取旧头 n，若为空就返回空或报错；否则尝试把头从 n 改为 `n.next`。成功的 CAS 确定了这次非空弹出在抽象栈中的先后位置，称为**线性化点**。有了它，就可以把交错执行的操作与某个合法的串行栈操作顺序对应起来。

```text
教学伪代码：CAS 返回旧值；暂不考虑节点回收
push(e):
    n = new Node(e)
    repeat:
        old = atomic_read(head)
        n.next = old
    until CAS(&head, old, n) == old

pop():
    repeat:
        old = atomic_read(head)
        if old == null: return EMPTY
        next = old.next
    until CAS(&head, old, next) == old
    return old.element
```

**与原文的区别：** 第 9–11 页在每次重试时都 `new Node`，教学版将分配移到循环外，失败后重设链接。课件局部变量跨出 `do` 的作用域、混用类与 C 地址符号等，也表明它不是可直接编译的语言程序。第 10 页尚未检查空栈，第 11 页才补上，应以完整阶段理解。

![栈的 CAS 与进展说明](Images/03-non-blocking/pdf_p011.png)

这里的重试还有一个有用性质：强 CAS 因头指针发生变化而失败时，别的线程已经成功更新过头。只要相关底层步骤满足假设，持续的竞争就伴随着成功更新，这给出了 lock-free 的论证方向。

不过，成功者不一定轮到自己。一个线程可能每次都比别人晚一步，始终重试，所以这个更新核心没有 wait-free 的个体步数界。分配与回收是否满足所需进展假设，还要单独检查。

## 队列为什么比栈多一个困难（第 12–19 页）

栈的压入和弹出都围绕同一个 head。队列则要求先进先出，入队在尾部接节点，出队从头部取元素。队列原来为空时，一次入队还可能同时影响 head 和 tail。

带锁版本能够保护这组修改，但单字 CAS 只能更新一个位置。非阻塞队列因此需要重新安排结构，让操作先完成一个关键修改，剩下的状态再逐步维护。

课件引入一个哨兵节点（fake/dummy）：`head` 指向哨兵，`head.next` 才是第一个有效元素。这样，空队列也有节点可作为连接起点。`tail` 用来帮助找到末端，允许暂时落后。

读后面的动画时，始终检查三个不变量：head 的后继是第一个有效元素；从 head 与 tail 出发沿链接前进，最终会相交；两条路径的末端都指向最后一个已入队节点。它们允许辅助指针不够新，却要求链的结构始终可用。

![允许尾指针滞后](Images/03-non-blocking/pdf_p018.png)

第 18 页特意把 tail 画到了当前 head 之前。只要旧节点及后继链接仍有效，入队者就还能沿它们追赶到末端。因此这份教学算法允许这样的滞后，也由此依赖旧节点的生命期：出队后不能立即任意释放它们。

## 单个入队如何完成（第 20–23 页）

初始时 head 和 tail 都指向同一个哨兵。构造元素 A 的新节点，其 `next` 为空。入队者从 tail 出发，若发现 `next` 非空，就帮助 tail 向后追赶；找到末端后，CAS 把该末端的 `next` 从空变成新节点。

**将末端空的 `next` 成功改为 A，就是这次入队的线性化点。** 此时，从队列链上已经能找到 A。随后移动 tail 只是让下一位入队者更快找到末端；即使这次辅助 CAS 失败，也无需撤销入队，因为 tail 可能已由别人推进。

## 两个入队者如何互相帮助（第 24–36 页）

动画让 B 和 C 同时准备接到 A 后面。它们都可能观察到 `A.next==NULL`，但只有一个能成功把它改成自己的节点。假设 B 先接入，却在更新 tail 前暂停：

| 步骤 | 已连成的链 | tail 的可能位置 | C 该做什么 |
|---|---|---|---|
| B 尚未链接 | fake → A | A | 尝试空 next |
| B 链接成功 | fake → A → B | 仍为 A | 发现 A.next 非空 |
| C 帮助追赶 | fake → A → B | 推进到 B | 沿新末端继续 |
| C 链接成功 | fake → A → B → C | B 或 C | 尝试推进 tail 后返回 |

![C 帮助 B 推进尾指针](Images/03-non-blocking/pdf_p031.png)

看图中的两种位置：B 已经接在紫色链上，而 C 仍由自己的局部变量指向，尚未入队。法语旁注说明，C 的执行者正在替 B 推进 tail。借助这种帮助机制，已经完成的链接不必等待原线程恢复，后来者也能补上维护步骤。

## 出队为什么移动的是哨兵（第 37–40 页）

读取旧 head 为 res，若 `res.next` 为空，队列在该观察点为空；否则尝试把 head 从 res 改成 `res.next`。成功后返回后者的元素。该节点成为新的哨兵，旧哨兵退出有效队列路径。

![A 成为新哨兵](Images/03-non-blocking/pdf_p039.png)

**图解：** 返回 A 的值，不等于把 A 的节点立即删掉。新的 head 正指向 A，下一次出队从 A 的后继取值。第 37–39 页使用 `value`，前面的结构定义写 `element`，这是原课件字段命名不一致，教程统一称元素值。

这里要分清抽象操作已经生效与某个函数已经返回。成功连接新节点或推进 head，分别使入队、出队产生抽象效果；推进 tail 则属于帮助维护，未必完成一个新的队列操作。

所以分析失败重试时，需要先确定失败的是哪一次 CAS，再结合有限链的追赶过程判断进展。只说 CAS 失败了，所以别人一定已经返回，并不足以证明这个队列 lock-free。

## 有序链表：删除为什么要分两步（第 41–48 页）

考虑 `A → B → C`。线程甲想删除 B，计划把 A 的后继改成 C；线程乙想在 B 后插入 X。如果甲先读了旧后继 C，而乙已经把 X 接到 B 后面，甲随后直接绕过 B，就可能一起丢掉 X。

Harris 式算法给删除增加一个中间状态：先把 B 标为已删除，使后续操作不再把它当作有效节点，再尝试从链上绕过它。这两步分别叫**逻辑删除**和**物理摘链**。课件用白色表示有效、灰色表示已逻辑删除；后续任何遍历者都可以帮助完成摘链。

插入者需要同时确认 B 尚未删除、B 的后继也没有改变。若颜色和 B 的 `next` 分开存放，只比较 next 的 CAS 就可能漏掉颜色变化。课件因此将两项状态编码在同一个可 CAS 的值中，并用指针最低位记录删除标志：

```text
pointer(v) = v 去掉最低位
mark(v)    = v 的最低位
```

第 48 页的 `ptr & -2` 表达清除最低位的意图。在具体 C 实现中须确认对齐保证、`uintptr_t` 与掩码类型、指针表示及原子访问方式；图中的位操作不自动在所有平台上成立。标的是当前节点自己的 next 域，不是随意给前驱链上的箭头加颜色。

## 遍历与帮助摘链（第 49–59 页）

读这段代码最容易混淆的是 `pred` 的间接层。它保存的是指向当前节点的**链接字段地址**：当前节点在表头时，这个地址是根指针的位置；走过一个节点后，它成为 `&cur->next`。

因此，修改 pred 所指的内容，就能改变谁连向当前节点。无论删除的是表头还是中间节点，都可以沿用同一套链接更新方法。

遍历遇到灰色节点 cur，就尝试用 CAS 将 `*pred` 从 cur 改为它的真实后继。成功以后，pred 仍指着同一个链接字段，只是这个字段已经指向下一个节点，所以代码在这里 `continue`，重新检查它。

若 CAS 失败，说明这处连接关系已经变化，需要重新寻找。可能是前驱被标记，也可能是两者之间插入了新节点。把成功后的 continue 误读为继续向后移动 pred，会跳过本应检查的节点。

## 删除 17：操作成功与摘链成功不是一回事（第 60–67 页）

在 `12 → 17 → 22` 中寻找 17，先读取 17 的 next，再 CAS 把该值改成“同一指针加删除位”。这次成功标记可以作为逻辑删除的线性化点。随后尽力把前驱链接改为 22。

![先标记，再帮助摘链](Images/03-non-blocking/pdf_p060.png)

如果另一个线程恰好在 12 与 17 之间插入 14，原来的摘链 CAS 会失败。课件第 65–67 页说明：即使 17 仍物理地在链上，逻辑删除已经完成，未来遍历者可以帮忙清除。不能因为没有立即摘掉节点，就报告删除从未发生。

第 68–69 页补全“没找到”的处理：到达空指针，或当前值已经大于目标值，可以停止。例如找 13，走到 17 即可判断不存在。这个结论依赖链表有序。

**原文边界：** 课件逐步代码包含未显示初始化的 `found`、未声明临时量，以及 `void` 函数中 `return 0` 等语言层不一致。它说明遍历与重试机制，并未定义完整集合 API，重复删除时的布尔返回值也需要额外设计。

## 插入 14：验证连接点仍有效（第 70–75 页）

寻找第一个大于 14 的节点，构造 `14.next=17`，然后 CAS 将前驱链接从 17 改成 14。成功 CAS 是插入的线性化点。如果前驱 12 被标记删除，它自己的 next 域会带标志，不再匹配未标记的期望值；如果别人已插入节点，也会不匹配。两者都应触发重找位置。

![插入 CAS 可能失败的两种原因](Images/03-non-blocking/pdf_p073.png)

**图解：** 插入所修改的是 pred 指向的链接，不是 cur 自己的 next。原图把“12 变灰”和“12、17 之间已有新节点”作为两个失败原因。课件没有拒绝相等键，因此它不能未经修改就被当作“不含重复值的集合”。

## 从教学图走到真实程序，还差内存回收（第 76 页及补充）

三个结构都可以沿同一条思路复查：先画出共享状态和需要保持的不变量，随后指出操作在哪次更新中生效，最后分析失败者继续重试时，系统是否仍取得进展。线性化点帮助判断操作结果，进展等级则描述操作能否完成，二者需要分别论证。

**补充，非原课件完整展开内容：** 逻辑删除、物理摘链、释放内存是三件事。一个节点已经不在链上，另一个线程仍可能持有旧指针。立即 `free` 会造成释放后使用；地址被回收再复用，还可能使 CAS 看到同一地址值而误以为状态没变，这就是常见的 ABA 风险。仅给指针加版本号，并不能单独解决旧指针解引用的安全性。

前面的算法分析都依赖同一前提：节点在使用期间有效，地址也不会以破坏算法假设的方式被复用。真实实现要用垃圾回收、hazard pointers 或 epoch 等机制落实这一点，并重新检查分配和回收对进展保证的影响。安全回收算法超出本讲展开范围；这里明确其必要性，供进入实验时继续核对。[Michael 的 hazard pointers 论文](https://research.ibm.com/publications/hazard-pointers-safe-memory-reclamation-for-lock-free-objects)

## 自检与判断要点

1. **某个线程不断 CAS 失败，是否反驳 lock-free？** 不一定；系统可能一直有其他操作完成，但它不是 wait-free。
2. **压栈失败后为什么要重设 next？** 旧的头可能已经变化，重用旧 next 会丢失别人的更新。
3. **入队真正完成在更新 next 还是 tail？** 在末端空 next 被成功改成新节点时；tail 更新是维护动作。
4. **出队后原第一个有效节点为什么还在？** 它成为新哨兵，返回其值与删除该节点内存是不同的事。
5. **删除位为什么和 next 一起 CAS？** 插入必须同时验证后继和当前节点是否已删除，分开验证存在竞态窗口。
6. **标记成功、摘链失败，删除是否一定失败？** 否，逻辑删除已发生，其他线程可以帮助物理摘链。
7. **能找到线性化点是否就等于完成正确性证明？** 不等于；还要证明不变量、返回值、所有分支以及对象生命周期，并单独分析进展保证。
