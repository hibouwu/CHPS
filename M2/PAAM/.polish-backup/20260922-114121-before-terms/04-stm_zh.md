## 从一把大锁到事务接口（第 1–4 页）

前两讲已经展示了两种困难。用一把大锁保护完整操作，容易理解，却会让本可独立进行的工作排队；改用细粒度锁或非阻塞结构，又要维护锁顺序、不变量、重试和对象生命期。

当程序想把两个各自正确的对象操作组合起来时，困难尤其明显：单独调用都正确，不代表组合过程对别人也是不可分割的。事务内存从这里出发，提供一组读写整体生效的接口。

这个接口写成 `atomic { ... }`。对于受事务协议管理的观察者，块中的修改应表现为整体执行。它描述的是一段代码的事务语义；标准 C 的 `_Atomic` 修饰单个对象，硬件原子指令则提供更低层的操作，三者的作用范围不同。

第 3 页让两个事务分别执行 x 加 1 与 x 乘 2。为对应图中的结果，先假设 x 初值为 21：加完再乘得到 44，乘完再加得到 43。两种结果都对应完整事务先后执行。读者应能依据这种串行顺序解释最终状态，而不能读到只完成了一部分的事务效果。

这里的初值 21 是由结果反推后补出的前提，原页没有显式写出。原图操作序列 `[b,c,e]` 也有标签问题：e 是右花括号，实际写回位于 d，应按读、计算、写回来理解。

把临界区改写成 atomic 可以隐藏锁的选择，但不是机械删除所有锁就能正确。事务外访问、I/O、不可重试操作及与其他同步机制的交互都需要单独定义。

## retry 等的是读过的状态发生变化（第 5–9 页）

线程与同步一讲中的条件等待，需要程序显式安排持锁检查、等待和再次检查。在课件采用的 STM 接口中，事务发现条件不满足时可以执行 `retry`。运行时放弃这次试执行，等它读过的相关状态发生变化后，再重新运行事务。

运行时之所以知道等什么，是因为它记录了**读集合**。例如事务检查队列是否为空，就对队列状态建立了读取依赖。登记等待必须与更新通知正确衔接，否则也会像条件变量使用不当一样丢失唤醒。这样的 retry 是基于状态变化的等待，避免了在原地反复读取的忙等。

再看组合操作：把元素从 src 队列移到 dst 队列。若先单独提交 `src.deq()`，随后才发现 dst 已满，源队列的变化已经公开，而目标队列还没有接收元素。

把出队和入队包进同一个外层事务，就能共同决定它们是否生效。内部任何一步触发 retry，整个 move 都从外层起点重来，两边不会留下只提交了一半的状态。

![嵌套事务的 retry](Images/04-stm/pdf_p008.png)

**图解：** 第 6 页把两个操作包入外层 atomic，第 8 页把重启箭头画到外层起点。这种扁平式嵌套语义是本课件的约定，不等于所有事务系统都支持相同的嵌套方式。

第 7 页的队列伪代码需留意两个原文问题：`addLast()` 缺少元素 e；`addLast` 与 `removeLast` 配对表现为后进先出。若按 FIFO 队列理解，应采用尾插头取。这些差异已在原文校对中保留，不影响此处借队列说明 retry 和组合，但不能照抄成完整队列实现。

`orElse` 让事务有另一个候选动作。先尝试左分支；若它需要 retry，就尝试右分支。课件用立即出队说明：有元素便取走，当前不能出队则返回空。

只有分支的 retry 触发这种选择，普通异常不能都按同样方式处理。若两个候选分支都 retry，运行时仍要根据相应的读取依赖等待，随后重新尝试。

## 冲突的本质：能否解释为事务整体执行（第 10–12 页）

要让 atomic 块整体生效，最直接的方法仍是一把全局锁：开始时获取，结束时释放。代价是事务彼此串行。

乐观实现尝试让事务先并发执行，到需要验证时判断能否接受结果。若这次执行无法与其他事务共同解释为合法的整体操作，就撤销或重试。下面的冲突例子说明验证要排除什么。

设事务 X 在内部先向 A 写 b，再写 c。对外只能观察到 X 整体执行的效果，另一个事务 Y 若读到了仅在中途存在的 b，就看到了不应公开的状态。

另一种问题发生在读者自身：Y 先后两次读取 A，中间 X 提交了修改，Y 因而取得两个版本。若系统没有专门允许这种语义，就无法把 Y 的读取解释成一个整体观察。两种情形分别促使我们考虑写入如何暂存、读到的状态如何验证。

| 方案 | 试执行时写哪里 | 成功时 | 失败时 |
|---|---|---|---|
| 延迟更新（redo log） | 私有写日志 | 验证后将日志发布到共享内存 | 丢弃尚未发布的日志 |
| 立即更新（undo log） | 共享内存，另存旧值 | 在合适保护下确认提交 | 按旧值恢复 |

redo 先把修改放在私有日志，其他事务在试执行期间不会直接读到这些中间值。提交时仍需安全地发布整组修改，不能把日志中的位置逐个随意写出。undo 则已经动到了共享状态，必须配合冲突管理，避免别人在恢复前依赖了这些中间值。

两者把工作放在不同阶段：日志记录、提交验证和失败恢复的成本都要计算。事务多数成功或多数失败，可以帮助分析代价，但不足以单独决定哪种方案更快。

## 两种日志的图中过程（第 13–14 页）

第 13 页从 x=20 出发。两个事务各自读到 20，一个准备写 21，另一个准备写 40。若后者先提交，前者的读依据变旧，需要撤销或重新验证，不应再把 21 直接覆盖上去。

第 14 页从 `(x,y,z)=(3,20,30)` 开始。一个事务把 z 写成 `y+7=27`，另一个修改 y 为 `x*2=6`。为解决冲突，中止第一个事务后需要把 z 恢复到 30，而不能把第二个事务合法写入的 y=6 一并擦掉。图中最终 `(3,6,30)` 说明 undo 日志记录的是谁改了哪些状态。

## 什么时候检测冲突（第 15–16 页）

检测时机是日志方案之外的另一项选择。eager 在访问期间尽早检查冲突，通常需要在相关读写处插入检查代码；lazy 将更多验证推迟到提交阶段。

推迟检查可以减少某些执行中的工作，却留下一个问题：事务在到达提交点以前，可能已经根据无效的读值继续计算。后面的僵尸事务例子会具体展示这个风险。

HTM 借助硬件维护读写集合及推测状态；STM 在软件中记录与验证；HyTM 尝试结合两者。课件对“HTM 常用 lazy”“只能放进 L1”“STM 可以任意大小”的说法是简化：检测时机、容量与回退机制依具体实现，软件也受内存和其他资源限制。这里不把历史概括写成今天所有处理器的统一规格。

## 第一版 STM：每个位置配一个版本（第 17–22 页）

第一版 STM 给每个共享位置增加一个计数器，用它辨认数据有没有被修改。事务读取时记住位置和版本，写入时只记录自己的新值。到提交时取得提交锁，再检查此前读取的版本是否还有效；检查通过，才发布写入并更新版本。

读集合用于记录计算依据，写集合用于记录准备公开的修改。两者可能重叠，却不必相同。

课件例子初始值为 a=10、b=21、c=7、d=83、e=8。事务执行：

```text
a = a + b
c = a - e
b = c
```

按代码顺序跟踪本地状态。第一句得到 a=31，将它写进自己的日志；第二句使用的也应该是这个新 a，因此算出 c=23；第三句再把 b 记为 23。d 没有参与计算，e 只被读取。

这个小例子说明，即使共享内存尚未变化，事务也必须能看到自己的写入，否则第二句就会错误地使用旧 a。

![本地日志与提交后的内存](Images/04-stm/pdf_p022.png)

**图解：** 绿色列是值，粉色列是版本，不要在 OCR 表格中把两者并成一个数。提交后 a、b、c 的值变成 31、23、23，版本分别从 17、13、2 变成 18、14、3；d、e 不变。读集合和写集合不是同一个东西：e 需要验证却不用写回，c 可以被直接覆盖而不需要读取旧值。

## 只在最后检查，为什么可能来不及（第 23–35 页）

仅在提交时验证，未必来得及保护事务自身。第一个例子先检查 `x != null`，准备调用 `x.f()`；另一事务在中间提交了 `x=null`。如果调用时重新使用共享 x，却没有及时验证它是否改变，就可能拿到空引用。

第 28 页的“does not read x again”要与第 29 页结合理解，指的是缺少再次版本检查；语法上的 `x.f()` 仍然需要取得接收对象。

第二个例子说明，只保护重复读取同一变量还不够。设已提交状态总满足 x≠y，初始为 `(4,5)`，写者随后整体改为 `(217,4)`，修改前后都满足这个条件。

但另一个事务可能先读到旧 x=4，随后读到新 y=4。它组合出了 `(4,4)`，接着计算 `1/(t1-t2)`，就可能在提交验证之前出错。问题出在把不同状态中的值拼在了一起。

![不同版本拼出的无效状态](Images/04-stm/pdf_p035.png)

**图解：** 左侧保留先读到的 t1=4，右侧提交后把 y 变成 4，接下来读者只检查新 y 自己的版本仍可能接受它。问题不是每次读取是否原子，而是多次读取能否属于一致的状态。

这种已经失去有效读取依据、却还在继续执行的事务，被称为 zombie transaction。最后拒绝提交，可以防止公开错误结果，却无法撤回此前已经发生的异常、越界或不可撤销操作。

因此下一版算法需要更早判断：当前取得的版本，是否还属于本次事务可以接受的状态。课件用开始时保存的全局时钟来建立这个边界。

## 全局时钟定义这次事务能够读取什么（第 36–45 页）

课件用 G 表示下一次提交可使用的版本号。事务开始时保存 S=G，把它作为本次读取的版本边界。此前已完成的提交版本小于 S；读到大于或等于 S 的版本，说明遇到了不能纳入本次快照的新修改，需要中止。

除了检查这个边界，还要处理读到自己写入的情况，并在提交时复查读集合。整个流程如下：

```text
开始：S = G，清空读集合与写集合
读取 i：若写集合已有 i，返回私有写值
        否则原子取得 (value, version)
        若 version >= S，终止本次事务
        记录 i，返回 value
写入 i：只更新私有写集合
提交：取得提交锁
      验证读集合中每个位置的版本仍 < S
      用当前 G 标记本次写回
      完成全部写回后 G = G + 1
      释放提交锁
```

这里用 `>=` 而不是 `>`，是因为课件“先用 G 写版本，再增加 G”的约定。若实现改成先增加时钟再给事务分配提交版本，相应不等式也要一致调整，不能拼接两种方案。

动画第 38–45 页：右侧事务较早在时钟 90 开始；其他事务把 G 推到 100；左侧在 S=100 开始并读到旧 x=4。右侧提交时用版本 100 写入新 x、y，再把 G 改成 101。左侧接着读 y，看见版本 100≥S，于是立即中止，不会带着 `(4,4)` 继续做除法。

![版本 100 的提交与时钟 101](Images/04-stm/pdf_p044.png)

**图解：** 紫色圆圈分别是全局或事务保存的时钟，必须按位置区分；红色 100 是新值的版本，不是新全局时钟 101。两者在 OCR 中容易挤在相邻行。

## 用不可变的值—版本对避免读到拼接状态（第 46–51 页）

版本检查本身也依赖一个前提：读者拿到的值和版本必须相互对应。如果把两个字段分别原地修改，读者可能在中间取得新值与旧版本，进而作出错误判断。

课件把它们放进不可变的 `(value,counter)` 对象。提交者准备好新对象，再原子替换指针；旧对象的字段不再修改，读者便可以拿到匹配的一对值与版本。

事务状态包括读集合、写集合和开始时钟。`read` 优先返回本事务写集合中的值，确保能读到自己的写入；否则读取共享值对并验证。`commit` 在一把全局提交锁下复查读集合、发布新对象，最后增加全局时钟。

![提交检查与写回](Images/04-stm/pdf_p051.png)

**图解：** 只有“验证成功→全部写回→递增时钟”的组合在提交锁内完成。读取端虽然不拿这把锁，也必须按语言内存模型正确读取已发布对象和时钟；不能把课件普通字段直接搬进 Java 或 C 就假设可见性自动成立。

**原文边界：** 第 47–51 页混用 Java 风格类型与方法。`HashMap<int,int>`、`Map<int,Value> entry` 等不构成可直接编译的 Java；这里保留算法意图。旧的不可变对象也不能立即释放，仍需垃圾回收或其他安全回收方案。课件这一实现明确使用提交锁，所以事务接口本身不意味着底层 lock-free。

## 退避、外部副作用与性能（第 52–54 页）

事务失败之后还要决定何时重试。两个竞争者若总同时开始，可能反复发生相似冲突。随机指数退避将重试时间错开，并在连续失败时扩大等待范围，以降低持续冲突的概率。它是调节竞争的策略，并没有提供每个线程都能成功的保证。

**第 52 页勘误：** 原例在 `doTransaction()` 里设置 `n=16`，失败后递归调用自己。新的调用又把 n 设回 16，所以窗口不能按代码的意图持续增大，调用栈还会增长。

要保留退避状态，应让 n 在外层重试循环中持续存在，成功或决定放弃时再退出。这里说明的是原例需要怎样调整，并未将它实现为经过验证的运行库。

日志能恢复受管理的内存，外部动作却可能已经发生。例如事务发送了请求或写了日志文件，之后再 abort，对方收到的请求和文件中的内容不会因此自动消失。

课件用一个夸张的函数名强调这点。若要在事务中执行不可撤销动作，就需要在动作前协调提交能力；也可以把外部动作放在提交之后，并另行设计两者的衔接协议。

第 54 页写“无死锁、无饥饿”，但这是过强的概括：运行时仍可能使用锁，冲突事务也可能持续重试，程序还可能等待永远不会成立的业务条件。接口减少了手工锁顺序负担，并不自动证明全部进展性质。

课件的性能例子是在双核上让 100 个线程各递增计数器 10000 次：STM 无退避约 3.0 秒、有退避 0.48 秒、锁 0.19 秒。它说明这个高冲突工作负载中退避有帮助、锁仍更快；不是 STM、HTM 和细粒度锁在所有机器上的统一排名。

## 自检与判断要点

1. **事务内存的 atomic 是否意味着掉电后数据不丢？** 否，这一讲关注并发原子效果；持久性需另有协议。
2. **src 出队成功、dst 入队触发 retry 时，组合事务应怎样？** 整体撤销试执行并从外层重新开始，不能保留只出队的提交效果。
3. **redo 为何还需要安全的提交过程？** 多位置写回本身仍可能暴露部分状态，需版本及同步协议约束观察者。
4. **x≠y 在每个已提交状态中都成立，为什么读者仍可能除零？** 它混合了不同提交版本的 x 和 y。
5. **为什么本次写过的值要优先从 writeSet 读？** 事务必须能看到自己的写，否则 `a=a+b; c=a-e` 会用旧 a。
6. **为什么不可变值对也不能立即释放？** 其他读线程仍可能持有指向旧对的指针。
7. **随机退避是否证明无饥饿？** 否，它是减少冲突的策略，不能单凭随机等待建立确定的个体完成保证。
