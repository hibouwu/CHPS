## 一个程序运行起来后，系统管理什么（第 1–2 页）

启动两次同一个编辑器，磁盘上的程序文件可以相同，两次运行却各有自己的状态。这样的运行实例就是**进程**。操作系统负责让它们开始、运行和结束，并提供信号、管道、套接字等通信方式。

课件把进程近似比作一台完整机器的虚拟化，着重说明它拥有自己的地址空间和资源视图。进程通常不能直接访问另一个进程的内存。底层 CPU 和物理内存仍由系统管理、在进程之间分配，并非每个进程各占一台真实机器。

## 从函数调用理解线程（第 3–5 页）

先看一次普通函数调用。`main` 调用 `add(1, 2)` 时，执行过程需要记住传入的参数、计算中用到的局部变量，以及返回后该从哪里继续。课件将这些信息画成调用帧；嵌套调用把多个帧组织成栈。

```c
/* 原课件片段 */
int add(int x, int y) {
    int z = x + y;
    return z;
}
```

![调用帧和下一条指令](Images/01-threads/pdf_p004.png)

读图时从右侧的栈开始：`add` 的帧位于 `main` 之上，保存了 `x=1`、`y=2`、`z=3`。再看左侧箭头，它指向下一步要执行的 `return z`；返回以后，程序回到 `main` 继续输出。图上的大标注遮住了一部分底层文字，OCR 因此产生断词，不能将这些残片拼入代码。

如果系统此时暂停执行，稍后恢复，它既要找回这组调用信息，也要知道下一条指令在哪里。**线程就是系统可以调度执行的上下文**：课件用调用栈和下一条指令的位置来说明它，实际实现还保存寄存器等状态。

这幅图适合用来追踪调用和返回。至于编译后的具体布局，变量可能被放进寄存器，函数也可能被内联，不一定逐项对应图中的栈格。

## 一个进程如何容纳多个线程（第 6–7 页）

一个进程可以包含多个这样的执行上下文。线程各有调用栈和执行位置，同时共享进程的代码、全局数据和堆，因此可以一边处理不同任务，一边访问共同的数据。

各有栈，并不意味着栈地址相互隔离。只要获得一个仍然有效的对象地址，线程也可以访问另一个线程栈上的对象。决定访问是否安全的，仍是对象的生命期以及访问之间的同步。

课件从常见的单线程启动过程讲起：初始线程创建其他线程，操作系统再把它们安排到 CPU 上。几个线程轮流运行、执行步骤相互交错，就已经构成并发；如果它们在多个执行单元上同时运行，才发生了并行。后面分析错误时，只需要一次不利的交错，因此单 CPU 也可能出现并发错误。

`pthread_t` 用于表示线程标识，`pthread_self()` 返回当前线程的标识。不要把 `pthread_t` 无条件当成普通整数，也不要将它与 Linux 内核线程号混为一谈。

## 创建、结束与回收（第 8–11 页）

接下来用 pthread 接口把执行上下文创建出来。先读参数：调用者提供入口函数和参数，系统通过 `tid` 写回新线程的标识。

```c
int pthread_create(pthread_t *tid, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
```

入口函数 `start_routine` 接收一个 `void *` 参数，因此可以通过 `arg` 传入对象的地址。`pthread_create` 传递这个指针值，**不会替你复制指针所指的对象**；对象由谁持有、能存活多久，需要调用者安排。

其余两个参数负责线程信息：`tid` 指向接收新标识的位置；`attr` 描述线程属性，传 `NULL` 使用默认属性。课件省略了 `attr` 的 `const`，上面的声明按 POSIX 接口补齐。

创建成功以后，入口函数何时开始执行取决于调度，创建者也会继续向下运行。第 8 页直接从 `main` 返回，工作线程可能还没来得及输出，整个进程就结束了。因此，创建线程之后通常还要明确：程序由谁等待它完成。

线程从入口函数返回，或调用 `pthread_exit(retval)`，都可以结束自身的执行。与此区别的是进程退出：从 `main` 返回，或者任何线程调用 `exit`，会使整个进程结束。

读第 6 页“最后一个线程结束时进程结束”时，要同时记住第 9 页补充的这些情形。第 9 页中的 `start_rountine` 是拼写错误，指的就是入口 `start_routine`。

```c
int pthread_join(pthread_t thread, void **pretval);
```

调用 `pthread_join` 后，调用者等待指定线程结束，还可以取回它的返回值。返回值本身是一个指针，接口又需要把它写到调用者提供的位置，所以参数使用二级指针，写回目标是 `*pretval`。不需要结果时，可以传 `NULL`。

第 10 页用 `(void *)0x42` 演示传回一个指针值。这不说明地址 `0x42` 上存在可用对象；取回结果和解引用结果是两回事。

默认创建的线程处于 joinable 状态。执行结束后，它还保留供另一个线程 `join` 的状态和相应资源。detached 则把这类资源的回收交给系统，结束后不能再用 `join` 获取返回值。

这里回收的是线程自身的相关资源。线程曾经分配的堆对象可能还要由其他线程使用，是否释放、何时释放，都仍由程序管理。

把前面的参数传递与退出规则放在一起看：若参数来自创建者的局部变量，创建者返回以后，该对象就可能失效，而新线程仍准备使用它。将线程设成 detached 只改变回收方式，不能延长参数对象的生命期。

## 为什么共享一个整数也会出错（第 12 页）

账户余额从 1000 开始，一个线程加 100，另一个线程减 1。正确的串行结果应为 1099。课件把每个操作拆成读、计算、写回：

| 时刻 | 扣款线程 | 存款线程 | 共享余额 |
|---|---|---|---|
| 1 | 读到 1000，保存在自己的 `tmp` 中 | 尚未执行 | 1000 |
| 2 | 暂停 | 读到 1000，加 100，写回 1100 | 1100 |
| 3 | 用旧的 `tmp` 算出 999，写回 | 已结束 | 999 |

![课件中的丢失更新](Images/01-threads/pdf_p012.png)

**图解：** `fg abcde hij` 是图中字母标记的交错顺序。扣款线程已经读过旧余额，随后恢复运行时不会自动重读，所以覆盖掉了存款结果。局部 `tmp` 是各自的，共享 `balance` 才是冲突位置。

**模型边界：** 这是解释丢失更新的交错模型。在真实 C/C++ 中，多个线程无同步地读写同一个非原子对象，且至少有一次写入，会产生数据竞争并导致未定义行为。不能声称这段程序“只可能”出现图中的有限几种结果；加 `volatile` 也不能使整个读改写成为线程同步操作。

## 互斥保护的是一段操作（第 13–15 页）

余额错误发生在读取旧值到写回新值之间。因此需要把这整个更新过程放进临界区，让另一个相关操作等它完成后再开始。只保护最后一次写回，仍会允许两个线程事先读到同一个旧余额。

互斥锁有空闲和占用两种抽象状态。获取操作等到锁可获得，并使当前线程成为持有者；释放操作允许其他等待者继续。它们的原子效果由实现提供，下一讲将解释这种实现。

```c
/* 课件的存款临界区；扣款操作也必须使用同一把 m。 */
pthread_mutex_lock(&m);
int tmp = balance;
tmp = tmp + 100;
balance = tmp;
pthread_mutex_unlock(&m);
```

**所有参与余额更新的线程，都要遵守同一把锁的保护规则。** 上面操作中的 `m` 保护从读到写的全过程。若读取者绕过锁，或者存款和扣款各自使用不同的锁，原来的交错仍可能发生。

遵守这个规则的竞争操作只能依次观察完整更新，这就是课件所说的临界区原子效果。临界区内部仍有多条指令，持锁线程也可能被抢占；其他线程在它恢复并释放锁之前继续等待。

## 条件变量：等数据到达时，让出锁（第 16–17 页）

有了互斥锁，线程可以安全地检查消息状态，但还要解决消息尚未到达时怎么办。接收者若一直持锁等待 `msg != NULL`，发送者就拿不到锁，也无法设置消息。若先解锁再自行休眠，通知又可能恰好落在这两步之间，接收者睡下以后无人再叫醒它。

条件变量与互斥锁配合，协调检查条件、释放锁和等待通知这几个动作。先看接收者的写法，注意 `pthread_cond_wait` 前已经持有锁，并且它位于 `while` 循环内：

```c
pthread_mutex_lock(&m);
while (msg == NULL)
    pthread_cond_wait(&c, &m);
printf("Message: %s\n", msg);
pthread_mutex_unlock(&m);
```

`pthread_cond_wait` 将释放互斥锁与进入等待协调起来，使发送者有机会拿锁修改状态；等待结束时，它会重新取得这把锁，然后才返回。

**返回以后仍要检查条件。** 一次唤醒不保证消息状态满足要求：可能发生虚假唤醒，也可能在接收者重新拿到锁之前，其他线程又改变了状态。这就是代码使用 `while` 的原因。POSIX 对条件等待也要求依据共享状态谓词重新判断。[POSIX 条件等待](https://pubs.opengroup.org/onlinepubs/9799919799/functions/pthread_cond_clockwait.html)

发送方在同一把锁下设置 `msg`，调用 `pthread_cond_signal`，再释放锁。唤醒不会把锁立即转交给接收者。`signal` 至少唤醒一个等待者（如果存在），`broadcast` 唤醒所有等待者；被唤醒者仍需竞争锁并检查谓词。

![消息发送和条件等待](Images/01-threads/pdf_p016.png)

图中左侧负责写消息并通知，右侧负责持锁检查。保存消息是否到达这一事实的是 `msg`，条件变量只参与等待和唤醒。如果发送者先设置好消息，接收者稍后拿锁检查到非空，就可以直接继续，不需要补收一次过去的通知。

这只是一次消息传递的教学例子。反复发送时，还需要明确消费后如何清空状态、多条消息如何排队、字符串何时失效，不能把这段代码直接当作完整消息队列。

## 把生命周期与同步分开思考（第 18 页）

到这里，可以分别画出线程的生命周期和共享对象的访问过程。`create`、`exit`、`join` 说明线程从创建到结束、回收的关系；mutex 规定哪些状态更新必须互斥；条件变量处理条件尚未满足时的等待。每次数据到达通常不需要结束一个线程再 `join`，而线程最终结束时，也不能靠条件通知代替资源回收。

## 自检与判断要点

1. **两个线程分别有栈，为什么还能发生共享数据冲突？** 它们处在同一地址空间，可能访问同一全局对象、堆对象或通过指针暴露的栈对象。
2. **创建线程后，谁先打印？** 不能从创建接口推断两者的具体执行顺序；需要额外同步才能指定顺序。
3. **为什么只锁住 `balance = tmp` 仍不够？** 读取和计算可能使用过期状态，需要把整个关联更新作为临界区。
4. **条件等待为什么使用 `while`？** 唤醒不是谓词成立的证明，返回并重新持锁后必须检查。
5. **`signal` 发生在等待之前，接收者一定会永久阻塞吗？** 正确设计把条件记录在共享状态中；接收者先检查状态，若已经满足便不等待。
6. **detached 是否让线程脱离进程独立生存？** 否。它改变终止后的回收方式，不改变进程退出会结束线程的事实。
7. **锁住了代码是否就能随意释放里面用到的对象？** 否。锁的互斥协议和对象生命周期都要满足；其他使用者可能在下一次获得锁后仍要访问该对象。
