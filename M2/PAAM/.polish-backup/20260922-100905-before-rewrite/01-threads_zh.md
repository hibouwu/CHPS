## 一个程序运行起来后，系统管理什么（第 1–2 页）

程序文件记录指令和静态数据；**进程**是程序运行时的实例。同一个编辑器可以启动两次，得到各自的运行状态。不同程序也能同时运行。操作系统负责创建、终止、调度进程，并提供信号、管道、套接字等通信机制。

课件将进程近似比作“一台完整机器的虚拟化”：进程有自己的地址空间与资源视图，普通情况下不能随意读写另一个进程的内存。这是理解隔离的比喻，并不意味着每个进程都有独占的物理 CPU 或内存。

## 从函数调用理解线程（第 3–5 页）

假设 `main` 调用 `add(1, 2)`。调用过程中，需要保存参数、局部变量以及返回到调用者所需的信息。课件用调用帧表示这组信息，用栈表示嵌套调用的关系。

```c
/* 原课件片段 */
int add(int x, int y) {
    int z = x + y;
    return z;
}
```

![调用帧和下一条指令](Images/01-threads/pdf_p004.png)

**图解：** `add` 的帧在 `main` 的帧之上；图中 `x=1`、`y=2`、`z=3`，箭头指向接下来执行的 `return z`。返回后继续 `main` 中的输出操作。图内覆盖正文的标注造成了 OCR 断词，不能把那些残片理解成额外代码。

一个线程不仅有“正在执行哪个函数”，还要有“执行到函数的哪里”。课件由此引入线程：可以被 CPU 执行、被系统调度的执行上下文，包括调用栈和下一条指令的位置。实际实现还保存寄存器等状态。优化编译器可能把变量放在寄存器、内联函数，所以这张图是调用过程的教学模型，不是每次编译后的物理内存布局保证。

## 一个进程如何容纳多个线程（第 6–7 页）

同一进程的线程共享代码、全局数据和堆等地址空间，但各有自己的栈和执行位置。于是两个线程既能处理不同任务，又能通过共享对象合作。共享地址空间也意味着：一个线程拿到另一个线程栈中对象的有效地址后，可以访问它；“各有自己的栈”不等于地址被隔离。

课件从单线程启动的常见过程讲起：程序启动后创建其他线程，系统把它们调度到 CPU 上。并发表示执行过程可以交错；并行表示它们确实在多个执行单元上同时进行。只有一个 CPU 时也可能存在并发错误。

`pthread_t` 用于表示线程标识，`pthread_self()` 返回当前线程的标识。不要把 `pthread_t` 无条件当成普通整数，也不要将它与 Linux 内核线程号混为一谈。

## 创建、结束与回收（第 8–11 页）

课件中的创建接口为：

```c
int pthread_create(pthread_t *tid, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
```

**接口校对：** 课件省略了 `attr` 的 `const`；这里按 POSIX 接口补齐。`tid` 是写回新线程标识的地址；`attr` 描述属性，传 `NULL` 使用默认属性；`start_routine` 是入口函数；`arg` 是传给入口的参数值。传的是一个指针值，并不会自动深拷贝它所指向的整个对象。

创建成功后，新线程和创建者的先后执行顺序不确定。第 8 页的例子在创建之后直接从 `main` 返回，因此不能保证工作线程的输出一定发生。这是课件紧接着引入等待终止的原因。

线程可以从入口函数返回，也可以调用 `pthread_exit(retval)` 结束。课件第 9 页的 `start_rountine` 是拼写问题，含义是 `start_routine`。从 `main` 返回或某个线程调用 `exit` 会结束整个进程，不能与结束当前线程混淆。因此第 6 页“最后一个线程结束时进程结束”不是全部终止情形。

```c
int pthread_join(pthread_t thread, void **pretval);
```

`pthread_join` 等待指定线程结束，并可把它的返回值写到 `*pretval`。二级指针来自“要把一个指针结果写回给调用者”。如果不要结果，可以传 `NULL`。第 10 页的 `(void *)0x42` 只是演示返回一个指针值，不代表地址 `0x42` 上有可访问对象，更不能直接解引用它。

默认创建的线程是 joinable：终止后仍需由合适的调用者 `join` 以回收相应资源。detached 线程结束时由系统回收这类线程资源，不能再用 `join` 获取结果。线程退出并不自动释放它分配的全部堆对象；共享对象的生命周期仍须由程序设计。

**学习检查：** 把函数局部变量的地址传给线程后，创建者马上返回是否安全？只有在该对象确实活到线程最后一次使用之后才安全；让线程 detached 并不能延长局部变量的寿命。

## 为什么共享一个整数也会出错（第 12 页）

账户余额从 1000 开始，一个线程加 100，另一个线程减 1。正确的串行结果应为 1099。课件把每个操作拆成读、计算、写回：

| 时刻 | 扣款线程 | 存款线程 | 共享余额 |
|---|---|---|---|
| 1 | 读到 1000，保存在自己的 `tmp` 中 | 尚未执行 | 1000 |
| 2 | 暂停 | 读到 1000，加 100，写回 1100 | 1100 |
| 3 | 用旧的 `tmp` 算出 999，写回 | 已结束 | 999 |

![课件中的丢失更新](Images/01-threads/pdf_p012.png)

**图解：** `fg abcde hij` 是图中字母标记的交错顺序。扣款线程已经读过旧余额，随后恢复运行时不会自动重读，所以覆盖掉了存款结果。局部 `tmp` 是各自的，共享 `balance` 才是冲突位置。

**模型边界：** 这是解释丢失更新的交错模型。在真实 C/C++ 中，多个线程无同步地读写同一个非原子对象，且至少有一次写入，会产生数据竞争并导致未定义行为。不能声称这段程序“只可能”出现图中的有限几种结果；加 `volatile` 也不能使整个读改写成为线程同步操作。

## 互斥保护的是一段操作（第 13–15 页）

临界区是需要与其他相关代码段互斥执行的区域。这里要保护的是从读取余额到写回余额的完整过程。如果只在写回时加锁，两个线程仍可能在锁外读到同一个旧值。

互斥锁有空闲和占用两种抽象状态。获取操作等到锁可获得，并使当前线程成为持有者；释放操作允许其他等待者继续。它们的原子效果由实现提供，下一讲将解释这种实现。

```c
/* 课件的存款临界区；扣款操作也必须使用同一把 m。 */
pthread_mutex_lock(&m);
int tmp = balance;
tmp = tmp + 100;
balance = tmp;
pthread_mutex_unlock(&m);
```

这里的关键不变量是：任何一个要参与该保护协议的线程，在访问共享余额的相关状态时都持有 `m`。仅给写入者加锁、读取者绕过锁，或者每个线程使用不同的锁，都不能建立这个保证。

课件说临界区“原子地执行”，是指遵守同一同步协议的竞争操作看不到中间状态，不是说整个临界区变成了一条 CPU 指令，也不是说线程不能在临界区内被抢占。

## 条件变量：等数据到达时，让出锁（第 16–17 页）

接收者需要等待 `msg != NULL`。只用互斥锁还不够：若它一直持锁检查 `msg`，发送者就无法拿到锁更新消息。若它先解锁、再自行休眠，消息可能恰好在两步之间到达，从而错过通知。

条件变量把“等待某个状态变化”与互斥锁配合起来。课件示意的接收方为：

```c
pthread_mutex_lock(&m);
while (msg == NULL)
    pthread_cond_wait(&c, &m);
printf("Message: %s\n", msg);
pthread_mutex_unlock(&m);
```

`pthread_cond_wait` 在调用者持有互斥锁时进入，把释放锁与进入等待协调起来；返回前重新获取该锁。返回之后，线程必须再次检查自己的条件。原因既包括可能的虚假唤醒，也包括其他线程在它重新获取锁之前又改变了状态。POSIX 明确要求围绕共享状态谓词使用这种检查逻辑。[POSIX 条件等待](https://pubs.opengroup.org/onlinepubs/9799919799/functions/pthread_cond_clockwait.html)

发送方在同一把锁下设置 `msg`，调用 `pthread_cond_signal`，再释放锁。唤醒不会把锁立即转交给接收者。`signal` 至少唤醒一个等待者（如果存在），`broadcast` 唤醒所有等待者；被唤醒者仍需竞争锁并检查谓词。

![消息发送和条件等待](Images/01-threads/pdf_p016.png)

**图解：** 左侧修改共享状态并通知，右侧用 `while` 检查。真正记住“消息已经到达”的是 `msg`，条件变量本身不储存一张可供以后消费的通知票。若消息在接收者开始等待之前就已设置，接收者检查到非空即可直接继续。

这只是一次消息传递的教学例子。反复发送时，还需要明确消费后如何清空状态、多条消息如何排队、字符串何时失效，不能把这段代码直接当作完整消息队列。

## 把生命周期与同步分开思考（第 18 页）

`create`、`exit`、`join` 管理执行的开始、结束和回收；mutex 保护共享状态更新；条件变量允许线程在状态尚不满足时等待。`join` 不是用于每次数据到达的通用通知机制，条件变量也不代替线程资源回收。

对应实验：[线程与同步](../Labs/tp-threads/tp-threads.html)。建议先能画出自己的线程何时创建、何时退出、谁等待谁，再为共享对象标明保护它的锁和等待条件。

## 自检与判断要点

1. **两个线程分别有栈，为什么还能发生共享数据冲突？** 它们处在同一地址空间，可能访问同一全局对象、堆对象或通过指针暴露的栈对象。
2. **创建线程后，谁先打印？** 不能从创建接口推断两者的具体执行顺序；需要额外同步才能指定顺序。
3. **为什么只锁住 `balance = tmp` 仍不够？** 读取和计算可能使用过期状态，需要把整个关联更新作为临界区。
4. **条件等待为什么使用 `while`？** 唤醒不是谓词成立的证明，返回并重新持锁后必须检查。
5. **`signal` 发生在等待之前，接收者一定会永久阻塞吗？** 正确设计把条件记录在共享状态中；接收者先检查状态，若已经满足便不等待。
6. **detached 是否让线程脱离进程独立生存？** 否。它改变终止后的回收方式，不改变进程退出会结束线程的事实。
7. **锁住了代码是否就能随意释放里面用到的对象？** 否。锁的互斥协议和对象生命周期都要满足；其他使用者可能在下一次获得锁后仍要访问该对象。
