## Question 3

In order to measure the time required to read memory, a thread will read a large buffer multiple times. We call this thread the **test thread**. 

Then, we will add some noise to measure memory access performance when there is traffic generated by other threads, which we call **noisy threads**.

Write a C application that accepts the following arguments:

- **`test_pu`**: An integer indicating the processing unit on which the test thread runs.
- **`test_node`**: An integer indicating the NUMA node where the buffer accessed by the test thread will be allocated.
- **`test_buffer`**: The size of the buffer accessed by the test thread, in kilobytes.
- **`test_workload`**: The total number of kilobytes accessed by the test thread. For example, if `test_buffer` equals 1 and `test_workload` equals 2, the test thread will iterate through the entire buffer twice.
- **`test_config`**: Configures the noisy threads with one of the following values:
  - `none`: No noisy threads are executed.
  - `spread`: A noisy thread is run on each processing unit except the one used by the test thread. Each noisy thread accesses a buffer located in NUMA node `(n + 1) % number_of_nodes`, where `n` is the NUMA node of the processing unit running the noisy thread and `number_of_nodes` is the total number of nodes.
  - `overload`: Similar to `spread`, except all noisy threads access buffers located in a specific NUMA node (defined by the next argument).
- **`noisy_node`**: An integer specifying the NUMA node accessed by noisy threads in the `overload` configuration.

At this step, you only need to verify that the correct number of arguments is provided and extract their values.

## Question 7

Now, allocate the buffers accessed by the noisy threads.

Assume that noisy threads continuously and sequentially access 32 megabyte buffers. Since a 32 MB buffer does not fit inside an L3 cache, this guarantees that noisy threads will generate traffic to the memory controllers.

Allocate the buffers as follows:
- **`spread` mode:** On node `N + 1`, where `N` is the node on which the noisy thread runs.
- **`overload` mode:** On the specified `noisy_node`.

To allocate memory from a specific memory node, refer to the following snippet:

```c
char* buf = hwloc_alloc_membind(
    topology,
    32 * 1024 * 1024,
    numa->pus[0].node->obj->nodeset,
    HWLOC_MEMBIND_BIND,
    HWLOC_MEMBIND_STRICT | HWLOC_MEMBIND_BYNODESET | HWLOC_MEMBIND_NOCPUBIND
);
```

> **Note:** Replace index `0` with the appropriate processing unit index corresponding to `test_pu`.

## Question 8

The noisy threads must continuously access their 32 MB buffers (meaning the application will not terminate for now).

To ensure that noisy threads interact with main memory rather than hitting the L1 cache, each thread must access each cache line of its buffer only once per pass. Represent the buffer as an array of `struct cache_line`:

```c
struct cache_line {
  union {
    char _content[64]; // 64 bytes in each cache line
    int  value;
  };
};
```

A noisy thread must execute an infinite loop that accesses all `32 * 1024 * 1024 / sizeof(struct cache_line)` cache lines in the buffer by reading the `value` field.

> **Optimization Warning:** If you compile your application with optimization flags (`-O2` or `-O3`), the compiler will detect that the loop performs no meaningful computation and eliminate it. To prevent this, either compile without optimization or perform a computation (e.g., maintain an accumulator variable `r` adding values across iterations, and assign `r` to a global variable outside/after the loop).

## Question 10

Next, implement memory access logic for the test thread.

Instead of reading byte-by-byte, read full cache lines using `struct cache_line` to accurately measure memory access latency. Accessing `value` touches 64 bytes at once without adding overhead from extra reads.

To access `test_workload` kilobytes, access `num_access = test_workload * 1024 / 64` cache lines.

Modify your application to sequentially access `num_access` cache lines in the buffer. Wrap back to the start of the buffer whenever the index exceeds `test_buffer * 1024 / 64`.

Use `clock_gettime` with `CLOCK_MONOTONIC` to measure execution time. Divide the total elapsed time by `num_access` to calculate the average access latency per cache line.

## Question 11

Sequential access triggers hardware prefetching, which masks true memory access latencies.

To bypass hardware prefetching, access memory locations randomly. To avoid measuring the overhead of calling `rand()` inside the benchmark loop, pre-compute random indices and store them within the `value` field of each `cache_line`.

During execution, start at `cur = 0` and traverse to `cache_lines[cur]`.

> **Important:** Ensure every cache line in the buffer is visited exactly once per cycle when pre-building the pointer chain.
