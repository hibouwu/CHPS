## Exercice I: Course questions (6 points)

### Question 1: NUMA (2 points)

We assume a NUMA architecture consisting of four nodes A, B, C, and D. Each node contains 10 cores and is connected to a memory with a maximum throughput of 5 Gb/s. We suppose 4 interconnect links: between A and B, B and C, C and D, and D and A. Each link has a maximum throughput of 1 Gb/s.

We assume an application consisting of 40 threads, in which each thread generates memory accesses at a constant rate of 0.1 Gb/s. The application allocates and initializes the memory used during computation in the initial thread.

In this setting, which policy will give the best performance: **first-touch** or **interleaved**? Justify. For each policy, you can represent the throughput generated on the different links using a diagram.

> **Solution:**
> 
> We suppose that memory access is uniformly distributed across the virtual address space.
> We have 40 threads, each generating a load of 0.1 GB/s, resulting in a total generated load of 4 GB/s.
> 
> - **Interleaved policy:** We distribute the 4 GB/s load equally among each interconnect link, which means 1 GB/s per link. None of the links saturate. The memory controllers, with their 5 GB/s throughput, do not saturate either. The actual total throughput is thus **4 GB/s**.
> - **First-touch policy:** The maximum possible load generated by the application to node A (4 GB/s) does not saturate the memory controller of node A. However, since the combined maximum capacity of the links connected to A (AB and AD) is equal to 2 GB/s, node A will only process 3 GB/s: the 2 GB/s received via the links from nodes B, C, and D, plus 1 GB/s generated by node A itself (10 threads at 0.1 GB/s). The total throughput of the application is thus **3 GB/s**, which is lower than the 4 GB/s achieved with the interleaved policy.

### Question 2: Memory Model (2 points)

We consider four variables `ok1`, `ok2`, `msg1`, and `msg2`, all initialized to 0. We also consider the following code in which reads and writes are atomic:

| Thread 1 | Thread 2 | Thread 3 |
| :--- | :--- | :--- |
| `a. msg1 = 42;`<br>`b. ok1 = 1;` | `c. while(ok1 == 0) { }`<br>`d. msg2 = msg1;`<br>`e. ok2 = 1;` | `f. while(ok2 == 0) { }`<br>`g. printf("%d %d\n", msg1, msg2);` |

If we consider a relaxed memory model, what are all the possible outputs?
What are the possible outputs if the machine does not reorder writes with other writes, nor reads with other reads?

> **Solution:**
> 
> With a machine that neither reorders reads with other reads nor writes with other writes, if `<` denotes "executed before", we necessarily have:
> - $a < b$ and $d < e$ ($a, b, d,$ and $e$ are writes)
> - $f < g$ ($f$ and $g$ are reads)
> 
> However, we can still have $d < c$ and $e < c$ because $c$ is a read while $d$ and $e$ are writes. For this reason, the possible outputs are:
> - `"0 0"` with $d < e < f < g$ (then $a < b < c$)
> - `"42 0"` with $d < a < e < f < g$ (then $b < c$)
> - `"42 42"` with $a < d < e < f < g$ (then $b < c$)
> 
> With the relaxed memory model, the possible outputs remain the same.
> 
> *Note:* `"0 42"` is impossible because if `msg2 == 42`, then `msg1` must be `42` due to line $d$.

### Question 3: Persistent memory (2 points, more difficult)

We assume that our computer features the latest eADR technology. This technology ensures that, in the event of a power failure, there is sufficient power to flush data from the CPU caches into persistent memory.

On such a machine, is it still necessary to use the `pwb` and `pfence` instructions? Justify your answer.

> **Solution:**
> 
> - `pwb` is no longer required: any dirty cache line will eventually be written back to memory in case of a failure.
> - `pfence` is still required: eADR handles cache flushing on power loss, but it does not address out-of-order execution memory ordering.

## Exercice II: The radix tree (14 points)

In this exercise, we implement a radix tree. A radix tree associates keys with values and provides an interface with two main functions:

- `void* insert(char* key, void* value)`: Associates the key with the value. If a value is already associated with the key, `insert` returns the old value and replaces it with the new one. Otherwise, `insert` creates a new key-value association and returns `NULL`.
- `void* get(char* key)`: Returns the value associated with the key if it exists, or `NULL` otherwise.

A node in the radix tree is represented by the following structure:

```c
struct node {
    void* value;
    struct node* nexts[256];
};
```

When searching for a key, we traverse the tree letter by letter starting from the root. Technically, the root represents the empty string (0 characters). The `nexts` array of the root is used to locate nodes associated with single-letter strings. For example, if `root` is a pointer to the root node, then `root->nexts['a']` points to the node representing `"a"`.

When `root->nexts['a']->value` is not `NULL`, it gives the value associated with `"a"`. Otherwise, the key `"a"` is not present in the tree. The `nexts` field of `root->nexts['a']` is used to retrieve two-letter strings starting with `'a'`. For example, `root->nexts['a']->nexts['b']` points to the node for `"ab"`, and its `value` field stores the associated value.

In this first part, implement the radix tree without considering concurrent accesses (assume a single-threaded execution context).
