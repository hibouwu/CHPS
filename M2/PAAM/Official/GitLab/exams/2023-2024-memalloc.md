We consider the following code:

```c
                bool ok = false;
                int* p = NULL;

// thread 1                    // thread 2
void thread1() {               void thread2() {
  p = malloc(sizeof(*p));        while(!ok) { }
  ok = true;                     *p = 42;
}                              }
```

## Exercice II: A simple memory allocator (18 points)

In this exercise, we will implement a memory allocator.
Internally, the allocator manages **chunks**.
A chunk represents a memory region, which can be allocated or not.
A chunk consists of this structure:

```c
struct chunk {
  size_t size;
  union {
    struct chunk* next; /* next node when the chunk is free */
    char content[0];    /* the content of the chunk when allocated */
  };
};
```

The interface then consists of two functions:

* `struct chunk* alloc_chunk(size_t size)`: allocates a chunk of size `size`,
* `void free_chunk(struct chunk* c)`: frees the chunk `c`.

When a chunk `c` is free, it is stored in a global linked list named `free_list`.
In this case, `c->next` points to the next free chunk in the list `free_list`.
When a chunk `c` is allocated, it is not in `free_list`.
In this case, the `next` field is not used, and the user can store the content of an object in `c->content`.

In order to allocate a chunk, `alloc_chunk(size_t size)` finds the first chunk `c` large enough in the list `free_list`, and removes `c` from the list.
If `c->size - size` is greater than or equal to `sizeof(struct chunk)`, returning the whole chunk `c` would lead to memory waste.
In order to avoid this waste, in this case, `alloc_chunk` has to split the chunk into two by creating a new chunk inside `c`.
At a high level, the algorithm of `alloc_chunk` is thus:

* Find the first chunk `c` in `free_list` such that `c->size >= size`,
* Remove `c` from the list,
* If `c->size >= size + sizeof(struct chunk)`:
  * Create a new chunk `struct chunk* d = (struct chunk*)((uintptr_t)c + sizeof(struct chunk) + size)`,
  * Set `d->size` to `c->size - size - sizeof(struct chunk)`, and `c->size` to `size`,
  * Free the chunk `d`,
  * Return `c`.
* Otherwise (i.e., if `c->size < size + sizeof(struct chunk)`), simply return `c`.

### Part I: Lock-based version (8 points)

In this first part of the exercise, you will implement a lock-based version of the allocator.
You can assume that a global lock named `pthread_mutex_t mutex` exists.

#### Question 2: free_chunk (2 points)

Give the code of `free_chunk(struct chunk* c)`, which adds `c` to `free_list`.

#### Question 3: create_large_chunk (2 points)

Give the code of a `struct chunk* create_large_chunk()` function.
This function allocates a large chunk of 64\*1024\*1024 bytes, adequately initializes its `size` field, and returns it.
This function does not add the new chunk to the list: the function simply returns the new chunk.

#### Question 4: alloc_chunk (4 points)

Give the code of `alloc_chunk`.
If `free_list` does not contain any chunk larger than or equal to `size`, then `alloc_chunk` uses `create_large_chunk` to create a new large chunk.
In this case, `alloc_chunk` adds the new large chunk to `free_list`, and retries allocating a chunk.

### Part II: Lock-free version (10 points)

In this second part of the exercise, you will implement a lock-free version of the algorithm step by step.
For that, we will start by simply considering `free_list` as a lock-free stack.

#### Question 1: pop (2 points)

Give the code of a `struct chunk* pop()` function.
If `free_list` is NULL, `pop` returns NULL; otherwise, the function pops the first element from `free_list`.

### Question 2: push (2 points)

Give the code of a `void push(struct chunk* head, struct chunk* tail)` function.
`head` is a list that ends with `tail`.
The function pushes all elements from `head` to `tail` (both included).
Note that it is not necessary to traverse the list from `head` to `tail`.

### Question 3: free_chunk (1 point)

Give the code of the `free_chunk` function.

### Question 4: alloc_chunk (5 points, difficult)

Give the code of the `alloc_chunk` function.
By leveraging `push`, `pop`, and `create_large_chunk`, you can avoid using any atomic operations directly inside `alloc_chunk`.
For that, the principle is simply to `pop` the chunks one after another in order to find a chunk large enough, and to use `create_large_chunk` if no such chunk exists.
After the allocation, `alloc_chunk` simply has to use `push` to reinsert the popped nodes that represent remaining free chunks.
