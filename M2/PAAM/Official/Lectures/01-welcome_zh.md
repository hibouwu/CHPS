## 多个核为什么没有自动让程序变快（第 1–2 页）

多核机器（multicore machine）让多个任务有机会同时执行。要把这种机会变成程序的加速，需要决定怎样分工、怎样共享数据（shared data），以及发生冲突时谁先修改。这门课就从 C 程序和底层同步机制（synchronization mechanism）出发，逐步讨论这些问题。

课件展示的机器有 4 个插槽（socket），每个插槽 12 个核（core），共 48 个核。数据中心、桌面和手机都可以采用多核架构（multicore architecture）；图中的核数只是这台机器的配置。

![课件中的多核机器](Images/01-welcome/pdf_p002.png)

图中四个插槽对应不同的物理位置。不同插槽中的核可以同时执行，但彼此交换共享数据需要时间。后面讨论锁（lock）的争用（contention）、缓存一致性（cache coherence）和非均匀内存访问（non-uniform memory access，NUMA）时，都会回到这一点：增加执行者的同时，也增加了协调和传递数据的工作。

### 先看机器里的距离，再看程序的分工

**课堂要点：一台机器内部也有通信成本。** 老师沿着照片中的插槽、内存条和互连解释：核能访问某块内存，不代表每次访问距离都相同。不同插槽之间需要传递数据，内存位置也会影响访问成本。这里把机器比作一个缩小的分布式系统，是帮助理解位置与通信的类比；编程时仍要区分共享地址空间与通过网络交换消息的模型。

即使用 Python 调用并行库，真正的工作最终也要落到核、缓存和内存上。理解这些层次，可以帮助判断瓶颈来自计算、同步还是数据移动，而不只是不断增加线程数。

*课堂来源：[第一段](01-transcript-part1.md)，第 13–52 行。*

以账户存款为例，两个线程（thread）都要读取余额、加上存款额，再写回结果。若它们读到同一个旧余额，后写回的结果可能覆盖先前的修改。加锁可以让更新依次完成；不过，如果所有请求都依赖同一把锁，其他核就可能一直等待，无法发挥并行能力。

学习时可以始终围绕同一个程序追问：哪些状态由多个线程共享，一次更新怎样才算完成，等待和数据传递又花了多少时间。先把这些关系讲清楚，再比较实现的速度，才知道性能改善有没有牺牲正确性。

## 六个主题怎样接起来（第 3 页）

| 主题 | 要回答的问题 | 下一步为什么需要它 |
|---|---|---|
| 线程与同步 | 如何创建并发执行、保护共享数据、等待条件？ | 先能写出正确的基本程序 |
| 锁算法 | 互斥（mutual exclusion）究竟靠什么实现，为什么会争用？ | 理解简单应用程序接口（application programming interface，API）背后的硬件成本 |
| 非阻塞算法（non-blocking algorithms） | 不把整个操作放进锁里，如何协调更新？ | 分析比较并交换（compare-and-swap，CAS）重试、进展保证（progress guarantee）及内存回收（memory reclamation） |
| 事务内存（transactional memory，TM） | 能否把一组读写作为事务，冲突时重试？ | 从单个原子更新（atomic update）扩展到多位置操作 |
| NUMA | 同样是内存访问，位置为什么影响速度？ | 让数据放置和线程放置相互配合 |
| 非易失性内存（non-volatile memory，NVM） | 程序崩溃后，哪些修改真的保存下来了？ | 在并发正确性之外考虑持久性与恢复 |

### 后面的课为什么越来越靠近底层

**课堂要点：先会用锁，再追问锁本身怎么做。** 第一讲暂时把 mutex 当作可靠工具；第二讲会面对一个循环：锁也是共享状态，多个线程同时检查和修改锁时，怎样避免再次需要另一把锁？接着研究非阻塞结构如何协调更新，以及事务内存如何把一组读写包装为更容易使用的操作。抽象越方便，内部维护正确性和性能的责任往往越重。

**补充说明：测试结果与正确性论证要配合。** 录音中“48 核上跑了没崩就说明没 bug”的说法是课堂中的夸张表达。测试可以找到反例，却不能穷尽所有线程交错。学习时仍要说明共享状态必须满足什么关系，再用具体交错检查实现是否维持这些关系。

*课堂来源：[第一段](01-transcript-part1.md)，第 70–106 行。*

阅读顺序与实验顺序配合起来即可。先用线程和互斥锁（mutex）写清一个共享状态的更新过程，再追问 mutex 怎样实现。遇到指针（pointer）、内存管理（memory management）或系统调用（system call）的具体障碍时，回查相应基础材料。这样可以把先修知识用在眼前的问题上，不必等到所有补充课件读完才开始。

## 需要掌握的基础（第 4 页）

课件要求较好的 C 编程能力，尤其是指针和内存管理，以及进程（process）、进程间通信（inter-process communication，IPC）等系统知识。

读并发代码前，先练习追踪对象的生命期：指针指向哪个对象，由谁创建，谁还会使用它，何时才能销毁。比如，把函数局部变量的地址传给新线程以后，创建者可能先返回，而新线程尚未读取参数。这时关键就在于对象是否仍然存在。后面的链表删除、事务日志和内存回收，都会再次遇到这个问题。

### 基础薄弱时，先把第一份实验做透

**课堂要点：先自己写，再看参考答案。** 老师提醒，直接打开实验解答会跳过最重要的练习：决定共享什么、谁等待谁，以及程序何时可以结束。基础不齐的同学可以在第一份线程实验上多花时间，遇到困难再提问，不必为了追赶进度而只复制后面的代码。录音里的分数描述比较口语化，不能把“完成第一份实验”理解为自动取得某个分数的承诺。

复习时可以拿一小段代码，在纸上画出线程执行顺序，说明每个指针所指对象的生命期，并找出一次可能失败的交错。这与纸笔考核所要求的理解直接相连。

*课堂来源：[第二段](01-transcript-part2.md)，第 256–280 行；[第一段](01-transcript-part1.md)，第 109–127 行。*

<a id="self-check"></a>

## 自检

1. **48 个核是否意味着一个程序能快 48 倍？** 不保证。程序需要足够可并行工作，还要承担同步、通信、调度及内存带宽等成本。
2. **为什么要先研究互斥再研究更复杂的并发结构？** 互斥提供一个清楚的正确性参照，随后才能讨论缩小串行部分或用其他机制替代它。
3. **NUMA 与非易失性内存分别关心什么？** 前者主要关心访问位置及其成本；后者还关心掉电或崩溃后的数据是否存在、是否可恢复。
