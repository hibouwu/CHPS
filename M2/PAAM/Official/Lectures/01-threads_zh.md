## 一个程序运行起来后，系统管理什么（第 1–2 页）

启动两次同一个编辑器，磁盘上的程序文件可以相同，两次运行却各有自己的状态。这样的运行实例就是**进程（process）**。操作系统（operating system，OS）负责让它们开始、运行和结束，并提供信号（signal）、管道（pipe）、套接字（socket）等通信方式。

课件把进程近似比作一台完整机器的虚拟化（virtualization），着重说明它拥有自己的地址空间（address space）和资源视图。进程通常不能直接访问另一个进程的内存。底层中央处理器（central processing unit，CPU）和物理内存（physical memory）仍由系统管理、在进程之间分配，并非每个进程各占一台真实机器。

**课堂要点：程序文件与运行状态要分开。** 老师从 `int x = 32` 举例：程序描述一个初始值，运行以后某个实例可以执行 `x = 21`，另一个实例仍保有自己的值。多个终端各自运行 shell，也是同一程序拥有多份运行状态的例子。这里说程序文件是“静态的”，是在区分程序描述与执行状态，不是说磁盘文件永远不可修改。

进程隔离与进程通信也要一起理解：隔离使一个进程不能随意访问另一个进程的状态；确实需要合作时，再通过系统提供的通信机制交换信息。老师用消息应用与通知显示之间的协作帮助理解这种需求。这个例子的重点是职责分离和通信，不要求把某个实际应用固定理解为恰好两个进程。

*课堂来源：[第一段](01-transcript-part1.md)，第 136–187 行。*

## 从函数调用理解线程（第 3–5 页）

先看一次普通函数调用（function call）。`main` 调用 `add(1, 2)` 时，执行过程需要记住传入的参数（argument）、计算中用到的局部变量（local variable），以及返回后该从哪里继续。课件将这些信息画成调用帧（call frame）；嵌套调用把多个帧组织成栈（stack）。

```c
/* 原课件片段 */
int add(int x, int y) {
    int z = x + y;
    return z;
}
```

![调用帧和下一条指令](Images/01-threads/pdf_p004.png)

读图时从右侧的栈开始：`add` 的帧位于 `main` 之上，保存了 `x=1`、`y=2`、`z=3`。再看左侧箭头，它指向下一步要执行的 `return z`；返回以后，程序回到 `main` 继续输出。图上的大标注遮住了一部分底层文字，OCR 因此产生断词，不能将这些残片拼入代码。

如果系统此时暂停执行，稍后恢复，它既要找回这组调用信息，也要知道下一条指令在哪里。**线程（thread）是一种执行上下文（execution context），可以由系统调度（scheduling）执行**：课件用调用栈（call stack）和下一条指令的位置来说明它，实际实现还保存寄存器（register）等状态。

这幅图适合用来追踪调用和返回。至于编译后的具体布局，变量可能被放进寄存器，函数也可能被内联（inlining），不一定逐项对应图中的栈格。

### 为什么需要一层层的调用帧

**课堂要点：一次函数调用，需要自己的一份现场。** 同一个函数可能从不同位置被调用，也可能递归调用自己；每次调用的参数、局部状态和返回位置可能不同，不能只给函数名配一份固定存储。老师把建立调用帧类比为“每次调用都分配一块内存”，用于说明状态随调用产生，并不是说 C 每次调用函数都会执行 `malloc`。

以 `main → f → g` 为例，当前在 `g` 中运行时，仍要保留 `f` 和 `main` 尚未结束的调用信息。`g` 返回以后，恢复的是 `f` 中调用 `g` 之后的位置；再返回一次，才回到 `main`。这解释了为什么只记“正在执行函数 g”不够，还要知道整个调用关系及返回位置。

### 系统怎样暂停一个线程，再从原处继续

**课堂要点：把执行现场保存下来。** 老师用程序计数器和栈指针说明上下文切换：先保存线程 A 的现场，再装入线程 B 的现场，CPU 就可以沿 B 的执行流继续运行；恢复 A 时，它接着完成先前未完成的调用。

| 需要知道什么 | 图中的对应物 | 丢失后会怎样 |
|---|---|---|
| 接下来执行哪里 | 程序计数器；x86-64 中常用 RIP 表示 | 无法从暂停处继续 |
| 当前调用现场在哪里 | 栈指针；x86-64 中常用 RSP 表示 | 找不到当前栈位置 |
| 尚未结束的调用保留了什么 | 调用帧、局部状态及返回信息 | 不能正确完成计算与返回 |

**补充说明：两个寄存器是教学简化。** 实际还涉及其他寄存器、线程状态；跨进程切换还可能涉及地址空间切换。线程的“现场”也包括已经存在于内存中的栈内容，不能理解成仅靠两个数字就复制出了一个完整线程。

*课堂来源：[第一段](01-transcript-part1.md)，第 190–265 行。*

## 一个进程如何容纳多个线程（第 6–7 页）

一个进程可以包含多个这样的执行上下文。线程各有调用栈和执行位置，同时共享进程的代码、全局数据（global data）和堆（heap），因此可以一边处理不同任务，一边访问共同的数据。

各有栈，并不意味着栈地址相互隔离。只要获得一个仍然有效的对象地址，线程也可以访问另一个线程栈上的对象。决定访问是否安全的，仍是对象的生命期（lifetime）以及访问之间的同步（synchronization）。

课件从常见的单线程启动过程讲起：初始线程创建其他线程，操作系统再把它们安排到 CPU 上。几个线程轮流运行、执行步骤相互交错，就已经构成并发（concurrency）；如果它们在多个执行单元上同时运行，才发生了并行（parallelism）。后面分析错误时，只需要一次不利的交错，因此单 CPU 也可能出现并发错误。

### 为什么在同一个进程中安排多条执行流

**课堂要点：分工作业与分开职责是两种需求。** 老师给了两个例子：矩阵运算可以把不同列交给不同工作线程；交互程序可以让一个线程等待键鼠输入，另一个线程继续渲染。前者把一份计算拆开，后者避免某一项等待拖住其他职责。线程共享数据方便协作，也因此需要约定访问规则。

从操作系统调度的角度看，本课关注可运行的执行上下文；从程序组织的角度看，进程又提供共享地址空间和资源边界。因此，“进程包含什么”与“CPU 下一步运行谁”是两个不同问题。录音中“线程与进程没有区别”的表述只适合帮助理解调度现场，不能取消它们在资源共享和隔离上的区别。

*课堂来源：[第一段](01-transcript-part1.md)，第 268–304 行。*

## 创建、结束与回收（第 8–11 页）

接下来用可移植操作系统接口（Portable Operating System Interface，POSIX）标准中的线程接口（POSIX threads，pthreads）创建执行上下文。先读参数：调用者提供入口函数（start routine）和参数，系统通过 `tid` 写回新线程的标识。

```c
int pthread_create(pthread_t *tid, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
```

### 创建接口中，哪些是输入，哪个位置接收输出

| 参数或返回值 | 阅读方式 |
|---|---|
| `tid` | 给出一个存储位置，接口把新线程标识写到 `*tid` |
| `attr` | 描述创建属性；本讲主要传 `NULL` 使用默认值 |
| `start_routine` | 给出新线程开始执行的函数 |
| `arg` | 交给入口函数的一个指针值 |
| `pthread_create` 的返回值 | 表示调用成功或失败；成功为 0，失败为错误编号 |

**课堂要点：入口函数和参数共同决定新线程做什么。** 老师以矩阵分工为例：多个线程可以使用同一个入口函数，但参数告诉各自负责哪一块。新线程标识通过输出参数取得，不是 `pthread_create` 的函数返回值。

*课堂来源：[第二段](01-transcript-part2.md)，第 1–28 行。*

入口函数 `start_routine` 接收一个 `void *` 参数，因此可以通过 `arg` 传入对象的地址。`pthread_create` 传递这个指针（pointer）值，**不会替你复制指针所指的对象**；对象由谁持有、能存活多久，需要调用者安排。

其余两个参数负责线程信息：`tid` 指向接收新标识的位置；`attr` 描述线程属性，传 `NULL` 使用默认属性。课件省略了 `attr` 的 `const`，上面的声明按 POSIX 接口规定补齐。

创建成功以后，入口函数何时开始执行取决于调度，创建者也会继续向下运行。第 8 页直接从 `main` 返回，工作线程可能还没来得及输出，整个进程就结束了。因此，创建线程之后通常还要明确：程序由谁等待它完成。

### 结束当前线程与结束整个进程

线程从入口函数返回，或调用 `pthread_exit(retval)`，都可以结束自身的执行。与此区别的是进程退出：从 `main` 返回，或者任何线程调用 `exit`，会使整个进程结束。

读第 6 页“最后一个线程结束时进程结束”时，要同时记住第 9 页补充的这些情形。第 9 页中的 `start_rountine` 是拼写错误，指的就是入口 `start_routine`。

### 等待完成，并取回结果

```c
int pthread_join(pthread_t thread, void **pretval);
```

调用 `pthread_join` 后，调用者等待指定线程结束，还可以取回它的返回值。返回值本身是一个指针，接口又需要把它写到调用者提供的位置，所以参数使用二级指针（pointer to pointer），写回目标是 `*pretval`。不需要结果时，可以传 `NULL`。

第 10 页用 `(void *)0x42` 演示传回一个指针值。这不说明地址 `0x42` 上存在可用对象；取回结果和解引用结果是两回事。

**课堂要点：`join` 只约束它之后的执行。** 在课件的打印例子里，若 `main` 先打印，再 `join`，工作线程和 `main` 的两次打印仍可能以任意顺序出现。成功返回的 `join` 保证目标线程已经结束；它不能倒过来规定调用前的两个输出谁先发生。

**教学推演：** `create → main 打印 → join 返回 → main 退出` 是主线程的一条顺序；工作线程的 `打印 → 返回` 必须发生在 `join` 返回之前。满足这些约束的执行顺序可以不止一种。复习时先画这些必须成立的先后关系，再列可能的交错。

*课堂来源：[第二段](01-transcript-part2.md)，第 25–55 行。*

### 执行结束以后，为什么还会占用资源

默认创建的线程处于可等待回收状态（joinable）。执行结束后，它还保留供另一个线程 `join` 的状态和相应资源。分离状态（detached）则把这类资源的回收交给系统，结束后不能再用 `join` 获取返回值。

这里回收的是线程自身的相关资源。线程曾经分配的堆对象可能还要由其他线程使用，是否释放、何时释放，都仍由程序管理。

把前面的参数传递与退出规则放在一起看：若参数来自创建者的局部变量，创建者返回以后，该对象就可能失效，而新线程仍准备使用它。将线程设成 detached 只改变回收方式，不能延长参数对象的生命期。

**课堂要点：长时间运行的服务尤其需要明确回收责任。** 一个 joinable 线程结束后，其他线程可能过一段时间才来取返回值，实现必须保留供 `join` 使用的状态。若服务反复创建线程，却既不 join 也不 detach，保留的线程资源就可能不断累积。若根本不需要等待和取结果，可以选择 detached；它不保证业务工作已经完成，也不延长进程的生命期。

**接口校对：** 录音在这两处有犹豫和识别混乱。`pthread_join(tid, NULL)` 可以合法地忽略线程返回值；`pthread_detach` 的接口是 `int pthread_detach(pthread_t thread)`，没有布尔参数，也不用于把 detached 线程切回 joinable。参见 [POSIX join](https://pubs.opengroup.org/onlinepubs/9799919799.2024edition/functions/pthread_join.html) 与 [POSIX detach](https://pubs.opengroup.org/onlinepubs/9699919799/functions/pthread_detach.html)。

*课堂来源：[第二段](01-transcript-part2.md)，第 55–82 行。*

## 为什么共享一个整数也会出错（第 12 页）

账户余额从 1000 开始，一个线程加 100，另一个线程减 1。正确的串行结果应为 1099。课件把每个操作拆成读、计算、写回：

| 时刻 | 扣款线程 | 存款线程 | 共享余额 |
|---|---|---|---|
| 1 | 读到 1000，保存在自己的 `tmp` 中 | 尚未执行 | 1000 |
| 2 | 暂停 | 读到 1000，加 100，写回 1100 | 1100 |
| 3 | 用旧的 `tmp` 算出 999，写回 | 已结束 | 999 |

![课件中的丢失更新](Images/01-threads/pdf_p012.png)

**图解：** `fg abcde hij` 是图中字母标记的交错顺序。扣款线程已经读过旧余额，随后恢复运行时不会自动重读，所以覆盖掉了存款结果。局部 `tmp` 是各自的，共享 `balance` 才是冲突位置。

**模型边界：** 这是解释丢失更新（lost update）的交错模型。在真实 C/C++ 中，多个线程无同步地读写同一个非原子对象，且至少有一次写入，会产生数据竞争（data race）并导致未定义行为（undefined behavior，UB）。不能声称这段程序“只可能”出现图中的有限几种结果；加 `volatile` 也不能使整个读改写成为线程同步操作。

### 先说明什么叫“正确”，再寻找并发错误

**课堂要点：同一项误差，对不同应用的意义不同。** 老师比较银行余额与访问人数统计：余额要求每笔更新都被计入，粗略统计可能允许一定误差。因此分析算法前，应先写出所要求的不变式，例如“最终余额等于初始余额加上所有已完成的存取金额”。还要明确一次查询允许看到更新前还是更新后的状态。

**补充说明：允许近似不等于允许 C 数据竞争。** 应用可以规定误差范围，但实现仍需遵守语言和同步规则。可以设计合法的分线程计数再汇总等方案，不能用“只求大概”来证明上面的无同步普通整数读写合法。

*课堂来源：[第二段](01-transcript-part2.md)，第 88–121 行。*

### 不只是两个写入者：检查之后，状态还可能改变

**课堂要点：消息刚才存在，不代表使用时仍存在。** 老师在余额例子后加入消息接收场景：发送线程写入 `msg`，两个接收线程都要检查、打印，再清空消息。一个接收者可能刚通过检查，另一个就把消息处理并清空了。

| 时刻 | 接收者 A | 接收者 B | 共享状态 |
|---|---|---|---|
| 1 | 检查 `msg != NULL`，成立 | 尚未执行 | 有消息 |
| 2 | 暂停 | 检查、使用消息，然后置空 | 无消息 |
| 3 | 恢复，重新取 `msg` 用作字符串 | 已完成 | 取得空指针 |

这说明检查与使用之间也需要协调。向要求有效字符串的操作传入空指针不合法，不能依赖某个库碰巧打印 `(null)`，也不必等到真的崩溃才判错。表格仍是教学交错模型；真实 C 中还要满足前述无数据竞争的要求。

两个线程都只读一个稳定对象时，不会因为“读者有两个”就发生这种写入冲突。本例的关键是其他执行者会修改共享状态；清空消息的接收者本身也充当写入者。

*课堂来源：[第二段](01-transcript-part2.md)，第 121–142 行。*

<a id="mutex"></a>

## 互斥保护的是一段操作（第 13–15 页）

余额错误发生在读取旧值到写回新值之间。因此需要把这整个更新过程放进临界区（critical section），让相关操作互斥（mutual exclusion）执行，即等一个操作完成后再开始另一个。只保护最后一次写回，仍会允许两个线程事先读到同一个旧余额。

互斥锁（mutex）有空闲和占用两种抽象状态。获取操作等到锁可获得，并使当前线程成为持有者；释放操作允许其他等待者继续。它们的原子性（atomicity）由实现提供，下一讲将解释这种实现。

```c
/* 课件的存款临界区；扣款操作也必须使用同一把 m。 */
pthread_mutex_lock(&m);
int tmp = balance;
tmp = tmp + 100;
balance = tmp;
pthread_mutex_unlock(&m);
```

**所有参与余额更新的线程，都要遵守同一把锁的保护规则。** 上面操作中的 `m` 保护从读到写的全过程。若读取者绕过锁，或者存款和扣款各自使用不同的锁，原来的交错仍可能发生。

遵守这个规则的竞争操作只能依次观察完整更新，这就是课件所说的临界区原子效果。临界区内部仍有多条指令，持锁线程也可能被抢占（preemption）；其他线程在它恢复并释放锁之前继续等待。

### 锁自己也是共享数据，谁来保护它

**课堂要点：先检查空闲、再写成占用，并不能实现锁。** 假设 A 检查锁为空闲后暂停，B 也检查到空闲并设置占用；A 恢复后继续设置占用，就会出现两个线程都认为自己拿到锁的情况。问题仍出在检查与更新之间。这正是下一讲研究锁算法的起点，本讲先使用 pthread 提供的 mutex。

### `balance += 100` 为什么没有消除问题

**课堂要点：源码短，并不代表操作不可分割。** 老师把加法拆成取得旧值、计算新值、写回，提醒我们：即使某个目标平台把它编译为一条普通的内存读改写指令，也不能由“只有一条指令”推断它对其他核是原子的。需要由同步原语或适当的原子操作提供保证。

**补充说明：** 录音中的访存与加法纳秒数用于解释成本差异，不能当作所有机器上的固定延迟；实际访问还可能经过缓存。这里也不能进一步推导“锁总是低效”：锁的成本取决于临界区大小、争用和等待策略，后面的课程才逐步分析这些条件。

*课堂来源：[第二段](01-transcript-part2.md)，第 142–187 行。*

<a id="condition"></a>

## 条件变量：等数据到达时，让出锁（第 16–17 页）

有了互斥锁，线程可以安全地检查消息状态，但还要解决消息尚未到达时怎么办。接收者若一直持锁等待 `msg != NULL`，发送者就拿不到锁，也无法设置消息。若先解锁再自行休眠，通知又可能恰好落在这两步之间，接收者睡下以后无人再叫醒它。

### 从持锁等待，到反复检查，再到休眠

**课堂要点：既要让发送者进来，也要避免空转。** 接收者持锁等待会挡住发送者；在循环中反复解锁、重新加锁，虽给了发送者修改状态的机会，等待者却仍在消耗 CPU 做无用检查。若等待时间很长，更合适的方式是让等待线程休眠，等状态可能改变时再醒来。

“放锁以后自行睡眠”还会留下通知丢失的窗口：发送者可能恰好在放锁后、进入等待前完成通知。条件等待需要把释放互斥锁与进入等待协调为一个动作，关闭这个窗口。下面先看 API，再回到消息例子。

*课堂来源：[第二段](01-transcript-part2.md)，第 187–232 行。*

### `wait` 返回时，已经重新持有锁

条件变量（condition variable）与互斥锁配合，协调检查条件、释放锁和等待通知这几个动作。先看接收者的写法，注意 `pthread_cond_wait` 前已经持有锁，并且它位于 `while` 循环内：

```c
pthread_mutex_lock(&m);
while (msg == NULL)
    pthread_cond_wait(&c, &m);
printf("Message: %s\n", msg);
pthread_mutex_unlock(&m);
```

`pthread_cond_wait` 将释放互斥锁与进入等待协调起来，使发送者有机会拿锁修改状态；等待结束时，它会重新取得这把锁，然后才返回。

**返回以后仍要检查条件。** 一次唤醒不保证消息状态满足要求：可能发生虚假唤醒（spurious wakeup），也可能在接收者重新拿到锁之前，其他线程又改变了状态。这就是代码使用 `while` 的原因。POSIX 对条件等待也要求依据共享状态（shared state）谓词（predicate）重新判断。[POSIX 条件等待](https://pubs.opengroup.org/onlinepubs/9799919799/functions/pthread_cond_clockwait.html)

发送方在同一把锁下设置 `msg`，调用 `pthread_cond_signal`，再释放锁。唤醒不会把锁立即转交给接收者。`signal` 至少唤醒一个等待者（如果存在），`broadcast` 唤醒所有等待者；被唤醒者仍需竞争锁并检查谓词。

![消息发送和条件等待](Images/01-threads/pdf_p016.png)

图中左侧负责写消息并通知，右侧负责持锁检查。保存消息是否到达这一事实的是 `msg`，条件变量只参与等待和唤醒。如果发送者先设置好消息，接收者稍后拿锁检查到非空，就可以直接继续，不需要补收一次过去的通知。

这只是一次消息传递的教学例子。反复发送时，还需要明确消费后如何清空状态、多条消息如何排队、字符串何时失效，不能把这段代码直接当作完整消息队列（message queue）。

### 谁保存条件，谁负责叫醒线程

**课堂要点：条件由程序定义。** `msg != NULL`、队列非空、到齐人数达到目标，才是要检查的条件；`pthread_cond_t` 是协调等待者与通知者的对象，不会自动替程序计算这些条件。共享状态与 mutex、条件变量一起构成这里讨论的 monitor 使用方式。

录音还用内部等待队列解释 API 的设计动机。学习时可以保留“等待者需要登记，通知者需要找到它们”的直觉，但不能据此假定所有实现都使用某一种链表，或完全不需要内部同步；应用应该依赖接口保证。

### `signal` 和 `broadcast` 怎样选

**课堂要点：一次新工作，与所有人一起放行。** 在线程池中，如果一次只加入一份可由任意一个工作线程处理的任务，通常通知一个等待者即可。在线程屏障中，最后一个线程到齐后，其他等待者都可以继续，因此需要广播。决定因素是这次状态变化允许多少等待者继续工作。

**教学推演：四个线程的一次性屏障。** 在同一把锁下维护到达数 `arrived`。前三个线程逐一把它加到 1、2、3，发现 `arrived < 4`，便进入条件等待；等待释放锁，后来的线程才有机会增加计数。第四个线程把计数加到 4 后广播，再释放锁。被唤醒者依次重新拿锁，检查 `arrived < 4` 已经为假，才离开等待循环。

这只是一次性屏障的推演。若需要反复复用，必须区分轮次，不能简单清零计数，否则上一轮尚未离开的线程可能与下一轮混在一起。线程池若有不同类型的等待谓词，也要重新分析通知策略，不能机械地只调用一次 `signal`。

*课堂来源：[第二段](01-transcript-part2.md)，第 232–253 行。*

## 把生命周期与同步分开思考（第 18 页）

到这里，可以分别画出线程的生命周期（lifecycle）和共享对象的访问过程。`create`、`exit`、`join` 说明线程从创建到结束、回收的关系；mutex 规定哪些状态更新必须互斥；条件变量处理条件尚未满足时的等待。每次数据到达通常不需要结束一个线程再 `join`，而线程最终结束时，也不能靠条件通知代替资源回收。

对应实验：线程与同步（[中文版](../Labs/tp-threads/tp-threads_zh.html) · [英文原版](../Labs/tp-threads/tp-threads.html)）。建议先能画出自己的线程何时创建、何时退出、谁等待谁，再为共享对象标明保护它的锁和等待条件。

## 自检与判断要点

1. **两个线程分别有栈，为什么还能发生共享数据冲突？** 它们处在同一地址空间，可能访问同一全局对象、堆对象或通过指针暴露的栈对象。
2. **创建线程后，谁先打印？** 不能从创建接口推断两者的具体执行顺序；需要额外同步才能指定顺序。
3. **为什么只锁住 `balance = tmp` 仍不够？** 读取和计算可能使用过期状态，需要把整个关联更新作为临界区。
4. **条件等待为什么使用 `while`？** 唤醒不是谓词成立的证明，返回并重新持锁后必须检查。
5. **`signal` 发生在等待之前，接收者一定会永久阻塞吗？** 正确设计把条件记录在共享状态中；接收者先检查状态，若已经满足便不等待。
6. **detached 是否让线程脱离进程独立生存？** 否。它改变终止后的回收方式，不改变进程退出会结束线程的事实。
7. **锁住了代码是否就能随意释放里面用到的对象？** 否。锁的互斥协议和对象生命周期都要满足；其他使用者可能在下一次获得锁后仍要访问该对象。

8. **统计允许少量误差，是否就可以无同步地更新普通 C 共享整数？** 不可以。近似要求属于应用语义，语言层面的数据竞争仍须避免。
9. **为什么“先看锁空闲，再把它设为占用”不够？** 两个线程可能都在任何一方设置占用前通过检查，检查和取得所有权必须得到正确协调。
10. **四个线程做一次性屏障，最后一个只调用 `signal` 有什么问题？** 其余等待者都需要继续，单次 signal 不保证把它们全部唤醒，应广播并让各自重新检查条件。
11. **`join` 是否规定了工作线程与主线程的所有先后关系？** 它保证目标线程结束先于成功的 join 返回，不规定 join 之前那些独立操作的先后。
