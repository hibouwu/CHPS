Threads and synchronizations

My first threads

Write, in C, an application that creates N threads with pthread_create, where N is the first argument of the application. Each thread must write to the terminal "[tid] Hello, World i!!!", where:

  • tid is the thread identifier returned by pthread_self,
  • i is a number incremented by the main for each thread (0 for the first thread, 1 for the second and so on).
Added answer and approach · 1.a

Parse and validate N, keep the IDs of successfully created threads in an array of pthread_t, and start the workers with pthread_create. Each worker obtains its assigned index i, calls pthread_self(), and prints the requested message.

Give every worker its own argument whose lifetime covers the worker's access. Passing the same loop variable &i repeatedly is unsafe: the creator keeps changing it while workers may read it. A separately allocated argument per worker is one option; an argument array also works if it remains alive until all users finish. If main calls pthread_exit, workers must not continue using an array on main's stack.

Handle creation failures and join only successfully created threads. A single integer printf format is not portable for every implementation of pthread_t. The supplied hello.c illustrates the approach but fixes N at 20; adapt it to read N from the command line.

Reference: pthread_create.

The main function has now to print Main quitting at the end of the function. Launch several times your application with 3 threads. Why, sometime, the application write the main quitting before the three hello worlds?

Added answer and approach · 1.b

pthread_create starts a thread; it does not wait for that thread to print. Scheduling determines whether the creator or a worker runs next. Without additional synchronization, main can reach its own print statement first.

Creation order therefore does not establish output order. To make Main quitting appear last, wait for the workers to finish the relevant work, for example with the joins used in the later question. Sleeping for a fixed duration does not establish that guarantee.

Reference: Scheduling after thread creation.

中文版答案

Start your application with 20 threads several times. Why, often, the application writes less than 20 times hello world?

Added answer and approach · 1.c

Returning from main terminates the entire process, including workers that are still running or have not yet been scheduled. If main reaches its end quickly, some workers may never reach printf, so fewer than 20 lines appear.

The number of observed lines is not a thread-limit measurement. Check that all 20 calls to pthread_create succeeded, then check how main waits or exits. The following questions change the exit timing with pthread_exit or joins.

Reference: Returning from main and thread termination.

中文版答案

Add a call to pthread_exit at the end of main. Why, now, the application systematically write 20 times hello world when you start it with 20 threads?

Added answer and approach · 1.d

pthread_exit terminates only the calling thread. When main terminates this way, the other threads can continue; the process exits normally after its last thread ends. Thus all 20 messages can be produced, assuming every creation succeeds, the arguments remain valid, and all workers complete normally.

This is not a wait followed by resuming main. pthread_exit does not return. Code placed after it is not reached, and a Main quitting message printed before it is not retroactively ordered after the workers' messages.

Reference: pthread_exit.

中文版答案

Ensure now that the application writes the main quitting after all the hello worlds.

Added answer and approach · 1.e

Create all workers first and save their IDs. Then call pthread_join for each successfully created thread. Print Main quitting only after every join succeeds. Since a worker prints before returning, this places main's message after all worker messages.

Do not create one thread and immediately join it inside the same creation loop: the next worker would not be created until the previous one finished, largely serializing the exercise. The order of joins does not prescribe the workers' relative print order; it only establishes that they have all finished before main continues.

Once all workers have terminated, main may return normally; pthread_exit is no longer needed to keep the process alive.

Reference: pthread_join.

A shared counter

First, add a global variable called counter initialized to 0 to your application. Then, ensure that each thread increments this variable after printing its hello world. Finally, modify the application in order to print the value of counter before the pthread_exit of the main.

When you run your application with 100 threads, why the printed counter is often smaller than 100? Modify your application in order to ensure that the counter is equal to the number of threads at end of the application.

Added answer and approach · 2.a

Separate two possible problems.

  1. Reading too early. Unless main waits for the workers, some increments may not have happened yet. If the complete joining step from 1.e is already present, this explanation no longer applies.
  2. Racing increments. counter++ on an ordinary integer is not an atomic operation. In a read–modify–write illustration, two threads both read 0, both compute 1, and both store 1, losing an update. Under the C memory model, unsynchronized conflicting accesses are a data race and cause undefined behavior; the possible outcomes are not limited to this simple illustration.

Protect every increment with the same mutex, and read the final count after main has joined all workers. No concurrent writers remain at that point. Any reads performed while workers are still running must follow the same synchronization rules.

An atomic counter with an atomic increment is another option, but main must still wait before checking the final result. Joining does not repair racing worker updates; atomic increments do not wait for all workers to finish. With correct synchronization and exactly one increment per successfully created worker, the final count equals the number of workers.

See also: Processes, threads and synchronizations.

中文版答案

Modify your application in order to print "Main quitting" only when the counter is equal to the number of threads.
Added answer and approach · 2.b

Use the counter as a shared predicate and let main wait on a condition variable until it reaches N.

  • Each worker prints its Hello, World message first, locks the mutex, increments counter, notifies the waiter when the count reaches N, and unlocks.
  • Main locks the same mutex and checks while (counter < N), calling pthread_cond_wait(&done, &mutex) while the predicate is false.
  • The wait releases the mutex while sleeping and reacquires it before returning. Print Main quitting only after leaving the loop.

Recheck the predicate in a while loop, including after spurious wakeups. If the final notification happens before main starts waiting, the counter already records completion, so main skips the wait; it does not need the condition variable to remember an old notification.

Join the workers afterwards if they are joinable and their resources must be reclaimed. counter == N establishes completion of the work preceding each increment, not necessarily termination of every worker.

Reference: Condition waits and predicate checks.

Producer/consumer

In this exercise, we want to implement a producer/consumer. In detail, the main thread, called the producer hereafter, has to read lines from the standard input and to push them in a queue. The other threads, called the consumers hereafter, have to take these lines from the queue in the FIFO (first in first out) order and to print them.

We want to implement the queue with a linked-list. The first node of the list is the oldest enqueued line (first in), while the last node of the linked list is the newest enqueued line (last in). We also want to avoid following the whole linked-list to enqueue a new node. For this reason, you have to keep both a pointer to the first and to the last node.

First, implement a unicast queue: only a single consumer has to take the messages from the queue. You have to ensure that a consumer thread sleeps with pthread_cond_wait when the queue is empty. Don't forget to free a node of the linked list when it is consumed.
Added answer and approach · 3.a

Maintain head and tail pointers, a mutex, and a condition variable. Unicast means that each message is taken by one consumer; this first version uses only a single consumer.

The producer gives each input line independent storage, locks the queue, appends the node after tail, sets head as well if the queue was empty, updates tail, and notifies the consumer. The consumer checks for an empty queue under the same mutex and waits in a while loop. When a node is available, it removes head and also clears tail if the queue becomes empty.

After removal, the single consumer owns the node exclusively. It can unlock, print the message, and release the message storage and node. Do not make all nodes point into an input buffer that the next read will overwrite. Use getline or suitable fgets handling for whole lines; %s reads whitespace-delimited words instead.

An optional completion protocol uses a closed flag protected by the same mutex. Set it and wake waiters when input ends. The consumer exits only when the queue is empty and input is closed; otherwise it drains remaining messages. The supplied spsc.c demonstrates synchronization using word input and an exit string, not complete line/EOF handling.

Atomic broadcast in shared memory (optional, 1/2)

Modify your application in order to implement a multicast queue: each consumer has to receive and to print each line (and in the FIFO order). In this question also, don't forget to free the nodes of the linked list.
Added answer and approach · 3.b

Broadcast requires every consumer to receive every message. Replacing pthread_cond_signal with pthread_cond_broadcast is insufficient: if the first awakened consumer still removes head immediately, the others cannot receive that message.

A simple baseline keeps all consumers at the current head. Give each node a sequence number and a remaining-consumer count initialized to the fixed consumer count N. Each consumer records the last sequence it handled so that it does not process the same node twice.

Under one mutex, a consumer waits until head exists and it has not handled that node, processes the message, and decrements remaining. Printing inside the mutex keeps this baseline simple. Only the last consumer, which makes remaining zero, removes and frees head, updates tail when necessary, and wakes the consumers for the next node. The producer also wakes relevant waiters when adding messages.

Every message is processed N times and each consumer preserves FIFO order, but faster consumers wait for slower ones. Atomic broadcast here concerns agreement on message order, not implementation with one hardware atomic instruction. The next question removes the per-node lockstep progression.

Atomic broadcast in shared memory (optional, 2/2)

With the broadcast, now, you can try to ensure that each consumer can consume a node even if the previous ones in the list are not consumers, which means totally desynchronizing the consumers (in your initial version, probably, all the consumers consume a node and then they all continue with the next one).
Added answer and approach · 3.c

Give each consumer an independent cursor to its next unread message, and keep a remaining-user count for each node. A fast consumer may advance after processing its current message without waiting for the others. It must not skip its own earlier messages, so its individual FIFO order is preserved.

A straightforward design can still use one global mutex. When appending a node, the producer publishes it to consumers whose cursors are at the end and waiting for new input. Under the mutex, a consumer copies its current message, saves the successor, advances its cursor, and decrements the node's count. It prints from the copy after unlocking, and prints before processing its own next message. The mutex protects queue state and cursors; it does not impose per-node lockstep across consumers.

A node may be unlinked and freed only after all consumers have passed it and neither the producer nor shared queue pointers still need it. If it was the last node, update tail consistently. One consumer finishing is not enough. A sentinel-based design is also possible, but the relationship between the final node and waiting cursors still needs an explicit protocol.

The supplied reference code needs a correction: mpmc.c calls pthread_mutex_unlock(&cons->mutex) after free(cons), accessing a freed object. Do not copy that order. Reclamation requires proving there are no remaining users and completing unlocking and any required synchronization-object cleanup; moving one free statement is not a substitute for that lifetime argument.
