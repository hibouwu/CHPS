5. Compiler flag 编译器向量化

使用 Release+`-O3 -march=native -fopt-info-vec-optimized` 编译 `sgemm`，收集向量化报告；用`perf`记录 `naive/ikj/blocked/omp with 1,2,4,8,16 threads/blas` 在不同编译器标志编译输出中的差异点

- 向量化构建：`cmake -S . -B build-o3 -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_FLAGS="-O3 -march=native -fopt-info-vec-optimized"`；`cmake --build build-o3 --clean-first` 的日志写入 `performance/vectorization_build.log`，其中 `src/sgemm.c` 的朴素、`ikj`、分块、OpenMP 核心循环均报告生成 64B/32B/16B SIMD 路径。
- 以原始 Release (`build/sgemm`) 与向量化版本 (`build-o3/sgemm`) 分别运行 `performance/compare-optimizations.sh`，CPU 绑在 `0-7`，`OMP_NUM_THREADS={1,2,4,8,16}`；结果存在 `performance/sgemm_perf_default.csv` 与 `performance/sgemm_perf_vectorized.csv`。
- 利用 pandas 合并两份 CSV 后可得：单线程 `naive` 平均加速约 1.30×，能耗下降 20–35%；`ikj` 提升 1.28–1.40×；`blocked`、`blas` 在 5–18% 区间。OpenMP 版本在 1–4 线程仍有 1.2–1.45× 收益，8 线程及以上受内存带宽与调度影响，性能改善趋于平缓乃至略降，但能耗总体仍较默认构建低。
- 结论：开启 `-O3 -march=native -fopt-info-vec-optimized` 对我们以缓存友好为主的内核帮助明显，但高线程场景的瓶颈主要源自访存/调度，后续可考虑多线程 + 手动分块或 NUMA 亲和性调优。


6. 调整 OpenMP 设置来优化性能和能耗

```bash
# 绑定核心 + 批量测试亲和策略（结果写入 performance/sgemm_omp_affinity.csv）
CORE_SET=0-7 OMP_THREADS=8 ./performance/experiment-omp-affinity.sh

# 手动复现 close / spread 等策略
OMP_NUM_THREADS=8 OMP_PLACES=cores  OMP_PROC_BIND=close  \
  perf stat -r 20 -e duration_time,power/energy-pkg/ taskset -c 0-7 ./build/sgemm omp 2048 512 512
OMP_NUM_THREADS=8 OMP_PLACES=cores  OMP_PROC_BIND=spread \
  perf stat -r 20 -e duration_time,power/energy-pkg/ taskset -c 0-7 ./build/sgemm omp 2048 512 512
```

- `performance/sgemm_omp_affinity.csv`（M=2048, N=K=512, 8 线程）显示：默认策略耗时 25.11 ms / 1.65 J；`OMP_PLACES=cores OMP_PROC_BIND=close` 将时间降至 24.95 ms（约 +0.6%）、能耗降至 1.61 J（约 +2.4%）；`OMP_PLACES=cores OMP_PROC_BIND=spread` 时间几乎不变但能耗略降至 1.64 J。
- `OMP_PLACES=threads OMP_PROC_BIND=close` 与默认几乎一致；强制将线程落在 `{0,2,4,6}` 并使用 `master` 会让耗时跃升到 42 ms、能耗 2.24 J（+68% 时间 / +36% 能量），不推荐。
- 结论：亲和性调优带来的收益在 1–3% 量级，作为细节优化仍有价值。性能优先推荐 `cores+close`，能效优先可选 `cores+spread` 或 `sockets+spread`；避免将多个线程堆叠在相同物理核心上。
- 与 `ikj`（单线程）对比：在向量化构建下，`sgemm_omp` 1 线程较 `ikj` 慢约 10%（因 OpenMP 开销），但能耗高出 ~25%；当线程扩展到 4 线程时，耗时从 27 ms 降至 ~17 ms（≈1.6× 加速），能耗略高；继续加到 8 线程后收益趋缓（~19 ms），能耗反而回升。16 线程（同等核心数）把耗时压至 16 ms 左右（比 `ikj` 的 23 ms 快 ~30%），能耗维持在 1.0–1.9 J 区间，说明并行化对于大矩阵仍能提供显著加速，但高线程下内存带宽成为主要瓶颈。

相对单线程：sgemm_omp 在 2–4 线程时速度提升 1.3–1.4×，能耗也同步下降约 10–20%；8 线程后提升趋缓（只剩 1.4–1.5×），但能耗基本持平或略回升。向量化版（build-o3）进一步把单线程耗时压至原来的 ~70%，能耗降到 65–80%，因此它是与“单线程基线”比较时的最佳对照。
线程数影响：能耗曲线在低线程区间下降（线程利用更充分、运行时间缩短），到 8 线程开始反弹，因为线程数继续增加时系统总功耗上涨但时间收益有限。16 线程则几乎没有加速（甚至稍降），能耗也趋稳。
单次运行能量 vs 线程：2–4 线程时能量消耗最低；再增加线程，能量止跌回升。原因是更多线程缩短了运行时间，但总功率上升更快——在 8 线程后“功率×时间”不再减少。
内存带宽对扩展性的影响：当线程数超过 8 时，访存成为瓶颈。矩阵乘法对内存带宽要求高，L3/DRAM 争用让额外线程无法“喂饱”计算单元，表现为性能不再随线程线性增长、能耗难以下降。适当的线程亲和（如 OMP_PLACES=cores）能略微缓解，但本质瓶颈仍是内存系统。
